# Cron Audit & Workflow Design — Learnings Log

Evidence rows. Each entry = ONE dated incident. Promote to a rule in
`workflow-design.md` / `autonomous-workflow-principles.md` after **≥3 dated
occurrences** of the same theme (per `auto-save-learnings.md`).

| Date | Theme | Evidence | Why it matters |
|---|---|---|---|
| 2026-06-17 | `cron_preflight` is NOT a lock | Read `cron-alert.sh` § `cron_preflight` — it kills duplicate google-mux daemons + cleans stale `/tmp/cron-lock-*` files >2h old. No per-script locking. Misreading this would silently let crons overlap. | Audit heuristics that credit `cron_preflight` for "locking" are wrong; locking is either inline LOCK_FILE, flock, OR `cron_run` timeout < crontab interval. |
| 2026-06-17 | `cron_run` provides heartbeat centrally | `cron_run` (cron-alert.sh L880+) writes `write_heartbeat "$script_name"` on `exit=0`. Scripts wrapped by cron_run get heartbeat-on-success for free. Audit's C-check (write_heartbeat in script) is conservative — internal call is redundant-but-harmless. | Don't fail C if `cron_run` covers it; consider exempting wrapped scripts. (Today the audit just flags both — additive heartbeat writes are harmless.) |
| 2026-06-17 | `cron_run` timeout-credit suffices for B (no overlap) | `cron_run` uses `timeout --foreground --kill-after=10` — guaranteed kill at timeout. When crontab interval ≥ 2× timeout, overlap is mathematically impossible. Most fleet crons pass B via timeout-credit; explicit locking only matters when interval ≤ timeout. | Drove cron_audit.py's B-check to credit `cron_run timeout < interval`. Cut B-fails from 27 → 8 with zero code change to scripts. |
| 2026-06-17 | Audit false-positives compound | First audit run flagged 47/57 missing locks → most actually had inline LOCK_FILE; F flagged 11/57 with bare `claude -p` → most were comment-text mentions or used `run_llm`; A flagged 9 → 4 were due to `$(dirname "$0")` regex break. Without fixing heuristics, every reported gap was suspect. | Always backtest an audit against known-clean cases AND known-bad cases before trusting its number. A high false-positive rate kills operator trust faster than a high false-negative rate. |
| 2026-06-17 | Config drift via duplicate files | `config/GCHAT-SPACES.yaml` (May 9) and `context/cache/gchat/GCHAT-SPACES.yaml` (Mar 19) were INDEPENDENT files, 2 months drifted. `cron-nightly-routine-preprocessing` read the stale one for ~2 months — nobody noticed. | When two scripts read the "same" config, make it a symlink (single source of truth) or extract to one canonical location. Drift is invisible until output diverges. |
| 2026-06-17 | Orphan producer pattern (script-without-scheduler) | Found 7 cron scripts with stated schedules in their headers (numbers-drill, ot-agent-mirror, 5 life-lane) that were never installed in crontab — zero heartbeats ever. Written but never consumed. | Drove §15b in `autonomous-workflow-principles.md` ("no orphan artifacts"). Every producer needs a named consumer in the same pass; if you write a cron, register it. |
| 2026-06-17 | Observer/consumer pattern violated by re-fetchers | `cron-ot-myclaw-chat-cache.sh` is the observer (caches 1 space). `cron-gchat-group-digest`, `cron-distill-learnings`, `cron-gchat-copilot` each re-implement their OWN fetch from gchat. Same pattern: read → process → write. Refactored to one multi-space observer (`cron-gchat-observer.sh`) + consumer-naming convention in `workflow-design.md`. | When N scripts hit the same API, ONE observer + N consumers reading cache is correct. Re-fetching duplicates cost and creates config drift opportunities. |
| 2026-06-17 | Audit needs helper-library exemption | `cron-workflow-self-eval.sh` is named `cron-*.sh` but is a sourced helper (no main). Audit flagged C/D/H/I/J for it. Fix: header keyword `helper` / `library` / `sourced by` exempts from those checks. | The "everything that looks like a cron" assumption breaks for `cron-*.sh` files that are actually libs. Marker convention: header comment carries `helper library (sourced by other cron scripts)`. |

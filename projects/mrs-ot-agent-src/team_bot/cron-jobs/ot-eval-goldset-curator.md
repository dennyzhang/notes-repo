[ot-eval-goldset-curator cron] Weekly, Sundays 08:00 PT. AUTOMATED gold-set lifecycle: append newly-resolved, confirmed-RC incidents from the archives into the eval gold set so the agent is continuously tested on FRESH cases it hasn't memorized — not a frozen 60. Operator-facing plumbing: output to the 1:1 only, never the team space.

**Why weekly (not daily):** each curation bumps `gold-set.json`'s `version`, and the eval relies on STABLE inputs for cross-run comparability. Weekly = the set is fixed within a week (runs comparable), grows once a week. Do NOT raise the cadence.

**HARD anti-gaming invariant:** selection and eligibility are BLIND TO EVAL SCORES. Never add/skip a case based on whether the agent passes it. Add/prune decisions key only off data properties (confirmed root cause, dedup, strata, source-exists). Teaching-to-the-test = the one way to corrupt the whole eval.

**Tool = the deterministic core** (`~/notes/users/dennyzhang/projects/mrs-ot-agent-src/tools/gold-set-curate.sh`, ABSOLUTE path — relative does not resolve from cron cwd). This cron only does the LLM prose→structured extraction; the tool does dedup / date-stamp / version-bump / cap / strata.

Steps:
1. **Status.** `python3 ~/notes/.../mrs-ot-agent-src/tools/gold-set-curate.sh report`. Note in-set strata, backlog, room-to-cap. If room-to-cap = 0 (set at MAX_CASES=180), skip to step 6 (`HEARTBEAT_OK`).
2. **Pick the most UNDER-REPRESENTED type** in the in-set strata (balance the set; today it is alert-heavy, so prefer `sev`/`post`). `bash .../gold-set-curate.sh new-ids --limit 20 --type <under-rep type>` → a JSON list of candidate archive ids + file paths.
3. **Extract each candidate** (the only LLM step). For each candidate `path`, `Read` the archive file and emit ONE gold case object:
   - `id`, `type`, `level` (from the Identity line), `input.title` (the `# S### — …` title), `input.signal_class` (Identity).
   - **`input.body` = the FIRE-TIME SYMPTOM ONLY** — the observable signal at incident open (from `## Overview` / `## Incident impact` / `## Timeline`). **NEVER leak the answer:** do NOT copy `## Root cause`, `## Remediation`, or `## Prevention` into the body. The body must read like what the bot would see *before* anyone solved it. (Leak = the eval measures memorization, not triage.)
   - `ground_truth.root_cause` (condense `## Root cause`), `ground_truth.owner` (Identity owner), `ground_truth.p_row` (map `## Error pattern mapping` CL-NNN → a known P-row, else `"none"`), `ground_truth.verdict` (`REAL_OT_FAILURE` / `DETECTOR_BROKEN` / `UPSTREAM_INFRA` / `NO_ACTION` as the archive supports), `ground_truth.confidence` (0–1).
   - **`eligible`**: `true` ONLY if the root cause is CONCRETE and CONFIRMED. Set `false` (with the case still emitted — the tool skips it) when the RC is `[postmortem field empty]`, "unconfirmed/not established", Report-quality "Insufficient" with no real RC, or confidence < 0.4. A case with no gradeable answer is not eligible.
4. **Merge.** Write the array to `/tmp/goldset-candidates.json`, then `bash .../gold-set-curate.sh merge /tmp/goldset-candidates.json`. The tool appends only eligible+new cases, stamps `added`/`source`, enforces the 180 cap, bumps `version`. Quote its literal output (added / dup-skipped / ineligible-skipped counts) — self-report from data, not narration.
5. **Prune (SAFE class only).** `bash .../gold-set-curate.sh prune` (read-only). It lists exact-dup ids + cases whose `source` archive vanished. Apply ONLY that safe class with `--apply` if any. **NEVER remove a case because the agent fails it** — hard cases are the point; removing them games the score. Hold-out/leak pruning is a separate operator-reviewed decision, not this cron's.
6. **Scoping-corpus curation (sibling lifecycle, same run).** The eval-SCOPING corpus (`eval/scoping-corpus.json`, engage/drop, feeds detection_recall + scoping_precision) has the SAME staleness problem as the gold set. Curate it here too (one cron, no proliferation) with its sibling tool `~/notes/.../mrs-ot-agent-src/tools/scoping-corpus-curate.sh` (ABSOLUTE path). Same SCORE-BLIND contract — add/prune key only off data properties, never decision-vs-label agreement.
   - a. `python3 ~/notes/.../mrs-ot-agent-src/tools/scoping-corpus-curate.sh report`. Note balance (engage:drop), `balance budget`, ENGAGE backlog. **Read the BALANCE WARN if present.**
   - b. **FROZEN-CORPUS INVARIANT (do not break):** eval-scoping.js short-circuits to this corpus only while it has ≥ FROZEN_MIN(30) cases; the tool guards this (refuses prunes below 30) and bumps `version` on every mutation so within-version runs stay comparable. You do not manage this by hand — just don't bypass the tool.
   - c. If `balance budget` > 0 AND ENGAGE backlog > 0: `bash .../scoping-corpus-curate.sh new-ids --limit 8` → candidate archive SEV ids. For each, `Read` the archive and emit a scoping case: `{id, label:"engage", source:"auto_detected_false" (or the alarm source if the archive shows an alarm fired), title: the symptom title, eligible:true}` — eligible iff it's a genuine in-org OT incident (it is, by archive construction; mark false only if the archive is a non-OT/out-of-org leak that slipped in). Write the array to `/tmp/scoping-candidates.json`, then `bash .../scoping-corpus-curate.sh merge /tmp/scoping-candidates.json`. Quote its literal output.
   - d. `bash .../scoping-corpus-curate.sh prune` (read-only; `--apply` ONLY for the SAFE dup/orphaned-source class it lists, never by score).
   - e. **HONEST LIMIT — do NOT try to auto-grow DROP cases.** Out-of-org/non-OT negatives are filtered at triage time and NEVER archived, so archive-mining can only grow the ENGAGE side; the tool refuses engage adds that push negatives below the floor. If report shows BALANCE WARN (negatives at/below floor), do NOT add engage cases — instead note it in the deliver line so the operator can hand-add drop cases or trigger eval-scoping's live noise-mining. This is an inherent tension between FREEZING for comparability and GROWING for freshness; surface it, don't paper over it.
7. **Deliver.** The notes write is auto-pushed by `ot-notes-commit-push`. If cases were added (gold set OR scoping corpus): send ONE line to the operator 1:1 by FOLDING into the existing curator thread (avoids the `# new-topic` hook-syntax friction — the home-space thread-reply hook blocks a bare send, and `# new-topic` must be a trailing shell comment, not a flag value):
   `meta google.chat.message send --space-name=spaces/AAQAVOjYc80 --reply-in-thread=spaces/AAQAVOjYc80/threads/awneEBwWB5g --text="[eval curator] gold +N (strata …) v<v>; scoping +M (now E/D, v<v>)[; BALANCE WARN: add drop cases]; backlogs gold <X>/scoping <Y>"`
   (curator thread = `awneEBwWB5g`, created 2026-06-12. If it ever 404s, start a new topic with a TRAILING comment: append ` # new-topic` AFTER the full command — it is a shell comment the hook recognizes, NOT a `--reply-in-thread` value.)
   THEN respond EXACTLY `HEARTBEAT_OK`. If 0 added to either: just `HEARTBEAT_OK`. NEVER emit a post-block/narration as the final response (the daemon delivers it to the team space).

Gold set: cap +20/run, balanced strata. Scoping corpus: cap 120, neg-frac floor 0.30, frozen-min 30. Both blind to scores. Source of truth = notes; each eval reads its updated corpus on the next run (version-stamped so comparisons stay within-version).

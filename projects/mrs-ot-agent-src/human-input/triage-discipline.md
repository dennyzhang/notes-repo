# Triage Discipline

Verification chain, per-fact tagging, Quality Rules 1-18 + R5b, diagnosis output template, signal-class taxonomy, stage-skill invocation, two-number confidence, stop conditions.

> **Back to:** [SKILL.md](../SKILL.md)

**Pattern match is the OPENING of triage, not the conclusion.** Every caller (interactive Claude, `team_bot.py` cron, WIB bot @mention, manual CLI) must run the verification chain before publishing a diagnosis. Stopping at "P01 fired with 68% confidence" without ground-truth verification produces an unfalsified guess.

## Verification chain (required for every non-trivial triage)

1. **Pattern hypothesis.** Run keyword-and-signal pattern match against `known_patterns.md`. State leading + secondary candidates explicitly. This is your starting point, not your answer.

2. **Ground-truth verification — MUST cover BOTH publishing AND trainer state for any T3 alert.** A publishing alert is never just about publishing — trainer state distinguishes a real failure from a bootstrap artifact. Run ALL:
   - `meta ai.model.instance list --model-id=<ID> --limit=30 --sort-by=creation_time --sort-order=desc --columns=instance_id,creation_time,snapshot_type,state -o table` — snapshot timeline
   - `meta ai.mast-job metadata --name=<JOB>` — current version + state
   - `meta ai.mast-job attempts --name=<JOB> -o json` — attempt history
   - `meta ai.mast-job insights --name=<JOB> --version=<CURRENT> --attempt=<CURRENT_AT> -o json` — analyzer flags
   - `meta ai.mast-job error --name=<JOB> --version=<PREV> --no-truncate -o json` — **CRITICAL** verbatim error from PREVIOUS failed version. Without it you only see post-restart silence. Never trust upstream "RUNNING = healthy" without re-pulling. (Source: 2026-05-02, `ig_textpost_feed_m2m_retrieval` v32 DataClientStuckException at 21:21 PDT was missed for hours.)

   Each `known_patterns.md` row has a *Verification Check* column — run it. Examples: P01 (FULL_SNAPSHOT blocking deltas) → verify FULL_SNAPSHOT in gap window; P05 (Trainer OOM) → CUDA OOM in error AND `analyze-zoomer-memory` >90% (falsified if mem util <70%); P19 (NCCL from publish stall) → NCCL error AND temporal correlation with `gmpp` events.

2-b. **Timing-window reasoning.** State three timestamps in every diagnosis: (1) trigger event, (2) alert fire time, (3) SLO window (MAJOR=1.2× cycle_minutes, CRITICAL=3.0× — see `mvai-ot/reliability/operations/monitoring.md`). If the alert fired within ~1 SLO window of a fresh trainer restart, default explanation is "post-restart bootstrap" — not "infra broken". Skipping this step is a common over-attribution.

2-c. **Read SEV's live GChat — MANDATORY when a chat channel exists.** Live thread is newer than snapshot. Extract `gchat_space_url` / `chat_url` from metadata; if `communication_channel` is non-GChat or absent, note `[no live chat channel — metadata-only]` and skip. Otherwise run `gchat read <space_id>` for ~20 most recent messages, parse for active hypotheses, paste links, ETAs, and contradictions to `root_cause` / `remediation`. Cite per-fact: `[VERIFIED via gchat read <space_id>]`. (Source: 2026-05-02 S657811 — metadata said "archiver restarted, awaiting catchup"; GChat said "~150 versions need manual deletion, won't be solved till next week".)

3. **Active-SEV cross-reference.** Run `meta sevmanager.sev list --in-progress --created-after="2 days ago" --columns=sev_number,title,sev_type,status -o json`. Cross-org Scribe / Hedwig / DPP infra SEVs often won't carry the OT tag but ARE the upstream cause. For each open SEV with adjacent signal class, surface the SEV id and connection. Don't assume the alert is isolated.

4. **Owner correction — model owner is PRIMARY, system-fix owner is SEPARATE follow-up.** Run `meta ai.model-series metadata --model-id=<MODEL_ID>` for `owner_unixname` and `oncall`. Diagnosis "Owners":
   - **Primary (this incident):** model `owner_unixname` + model oncall + product oncall (e.g., `p92_relevance_retrieval_oncall`).
   - **Source owner:** literal `assigned_user` (alerts) / `owner_unixname` (SEVs) from upstream JSON.
   - **OT-side escalation:** per-product routing from `team_bot_config.yaml`.
   - **Secondary follow-up (only if a system bug exists):** owner of any routing/config bug surfaced.

   Don't promote a system-bug fixer to primary just because they show up in fbcode commits. (Source: 2026-05-02 `ig_textpost_feed_m2m_retrieval` triage suggested lupaul as primary instead of model-owner ronghuang.)

5. **Hypothesis chain.** Take the leading pattern, test against (2). If contradicted, *write the falsification* and switch to the secondary. Standing hypothesis is the one surviving verification — not the highest-confidence pattern match.

## Per-fact tagging — VERIFIED vs INFERRED

Every load-bearing claim carries one of two markers:

| Marker | Means | Example |
|---|---|---|
| `[VERIFIED]` | Sourced from `meta` CLI / Scuba / capability output. Exact command must appear in Evidence Package. | `MAST v32 died 21:21 PDT [VERIFIED via meta ai.mast-job error --version=32]` |
| `[INFERRED, NOT PROVEN]` | Hypothesis from pattern-match / correlation / analogy. Not confirmed by direct data. | `S658056 is upstream cause [INFERRED — needs timeline correlation]` |

A real-incident diagnosis with no markers of either kind is wrong — both should appear. (Source: 2026-05-02 `ig_textpost_feed_m2m_retrieval` asserted "delta-only, never FULL_SNAPSHOT" at 80% confidence based on a single anomalous query; explicit `[INFERRED]` tagging would have surfaced over-confidence.)

## Quality Rules 1-18 + R5b (extracted from velvinfu 2026-04-30 incident, P2300957350; R9-R10 added 2026-05-08 from operator-shared paste GJqDYSlR6JPB96oFAOtruCpDcE1Gbr0LAAAz — Fei Ding S653266 IFR MTML delta-publish CPU OOM investigation; R11 added 2026-05-08 from S661157 (TIFU u2m m2128360468 / m2131533016 fbpkg expiry); R12, R13, R5b added 2026-05-08 from csanghera Workplace post validator-discrepancy harvest; R14 added 2026-05-08 from m2133142909 STUS-vs-trainer mistake hit 3x in one session; R15 added 2026-05-08 from m2133142909 / m2133154105 — operator-corrected: bot blamed P17 fire-app expiry, real root was disabled recurring flow 8921769; R16 added 2026-05-08 from m2132070936 — operator-corrected: alert was a false alarm because DENSE_DELTA doesn't apply to this model class, bot had the data but failed to elevate "alert misconfigured" to standing hypothesis; R18 added 2026-05-13 from S661843 — operator-corrected: bot diagnosed serving-stage failure but routed to mrs_online_training because of MRS-org tag, conflating org-scope with stage-scope)

| # | Rule | Mandate | Failure mode without it |
|---|---|---|---|
| R1 | **Baseline before anomaly** | Cite same job/metric in known-good window before claiming "broken/slow". Ex: "publish 42 min — earlier cycle 4 min". | Reader can't tell 42 min from normal. |
| R2 | **Layered hypothesis enumeration** | Enumerate every layer the symptom could live at, rule each in/out. No single-hypothesis. Ex: "BD writer 1.6 GB/s NOT bottleneck; Hedwig 2-26 MB/s IS." | Guess masquerading as diagnosis. |
| R3 | **Code-pointer on recommendations** | Every "fix X" cites file path + line. Ex: `trainer_config.py:618-633`. | 5-min file hunt to act. |
| R4 | **Tiered recommendations** | SHORT (≤1d, config flip/revert/JK); MEDIUM (≤1w, cross-team); LONG (weeks+, refactor). | "Async refactor" weighted same as "bump value". |
| R5 | **Soft cross-refs include verification** | Next-action MUST include verification command BEFORE any contingent fix. NOT "if X is upstream, do Y"; instead "first run Z to verify; if yes, then Y". | Soft refs promoted to action items on wrong premises. (Source: 2026-05-02 S657811→S658142.) |
| R6 | **Temporal consistency on suspect diffs** | SEV `first_occurrence_time` ≥ X's land time before naming X as regression source. Pull occurrences explicitly. | First-occurrence pre-dates the diff → at most amplifier, not trigger. |
| R7 | **Frequency-over-time inflection check** | For multi-day SEVs, plot occurrence frequency. Step-change → check diffs near inflection. | "Soft-warn → hard exception" pattern: latent gap tolerated for days, then a validator diff converts warn to exception. |
| R8 | **Entity multiplicity rule** | Pull SEV's full entity list before forming entity-specific hypothesis. Single → likely entity-specific config; multiple → systemic. | Per-entity fixes chased on systemic problem. |
| R9 | **Mechanism over conclusion** | When the diagnosis is a misconfig, perf regression, or resource exhaustion, name the data-flow chain (Phase A → Phase B → ...) and identify which phase the symptom emerges in. Ex: "delta publish has Phase 1 GPU (`delta_tracker.get_unique → torch.topk → GPU→CPU copy`, blocks training) and Phase 2 CPU async (Hedwig publish backlog). The CPU OOM comes from Phase 2 backlog, not Phase 1 selection mode." | Reader sees "X causes Y" without understanding *how*, can't extrapolate the fix to a sibling case, can't tell which knobs are mechanism-relevant vs cosmetic. |
| R10 | **Calibration anchors on numeric fix recs** | Every numeric knob change cites (a) typical safe value across the fleet AND (b) safe value for the offender's class. Ex: "Reduce `embedding_delta_percentage` to 25-50% (current 100%). Most models use 25% for non-critical tables, up to 100% only for user ID tables." Also cite preconditions when applicable: "Enable concurrent delta — but check memory headroom first (need ≥20% free during full publish)." | "Reduce X" without anchors makes the operator guess; under-tuning leaves the issue, over-tuning creates a new one. |
| R11 | **Root model vs served model — distinguish in every snapshot/staleness diagnosis** | When the symptom is on a served model id (snapshot stall, model age growing, deployment lag), the root cause may be on the upstream root training model id, not the served id. Every diagnosis MUST cite BOTH ids when they differ: `served_model_id=<X>, root_training_model_id=<Y>`. Before naming a fix, walk the lineage to confirm which side the failure lives on (TMS state, MAST job state, fbpkg expiration are root-side; serving errors, predictor age are served-side). Source: 2026-05-08 S661157 — original P38 attribution to served `m2128360468` was wrong; root cause was P17 on root training `m2131533016` (fire-app fbpkg expired). Conflating the two cost ~6h of misdirected diagnosis. | Diagnosis chases the wrong model id; fix proposed on serving side when root cause is upstream training; "snapshot stall" labeled as `Boxcar preemption` when it was `fbpkg expired`. |
| R12 | **Verify model_id ↔ MAST job linkage before connecting them** | Before reasoning "MAST job X is causing model Y's symptom", grep the MAST job's `application_metadata.flow_root_workflow_run_id` AND `model_entity_id` fields and confirm they match Y. Two facts adjacent in time on the same dashboard are NOT necessarily causally linked. Source: 2026-05-08 csanghera Workplace post triage — bot joined "MAST f1078664497 long-running" + "snapshots stale on m2125399403/m2125249288" into one hypothesis, but the MAST job actually wrote to m2125436031 (a different model). Validator caught it. | Two coincidentally-stale facts get welded into a fake causal chain; the real upstream (e.g. an open SEV) gets ranked secondary because the inferred chain feels more specific. |
| R13 | **Long-running ≠ stalled — require step-rate / progress signal** | "Job is 3x baseline duration" is NOT evidence of stuck. A run can take 3x longer for legitimate reasons (data shape, capacity, retries) and still complete cleanly. Before claiming a job is stalled, cite (a) trainer step rate / TensorBoard progress signal showing flatline, OR (b) a fresh `meta ai.workflow-run status` that the run actually ended in non-success state, OR (c) trainer logs showing no-op for >Nx the typical step interval. "no end_time" in cached metadata is NOT the same as "stalled". Source: 2026-05-08 csanghera triage — bot inferred f1078664497 was stalled at 19h vs 6h baseline; validator re-queried and found the run had completed at 13:48 PT (~19.4h, SUCCEEDED). | False alarms route operator attention to a job that is fine; misses the real signal (a cross-ref SEV that directly matches the symptom). |
| R14 | **Job-role verification — check `entrypoint` BEFORE assuming `mvai-training-online-<id>` is a trainer** | The MAST naming convention `mvai-training-online-<MODEL_ID>` is shared by **two distinct job classes**: (1) actual training jobs whose entrypoint is `train.py` / `mvai-train` / equivalent, and (2) SilverTorch update service (STUS) publish jobs whose entrypoint is `silvertorch/experimental/st_update_service/st_update_service.py`. STUS jobs do NOT train — they consume upstream root checkpoints and republish. **Before forming any "trainer is stuck / publishing / scheduler" hypothesis, run `meta ai.mast-job metadata --name=mvai-training-online-<id>` and grep `entrypoint`.** Branch the hypothesis space accordingly: trainer-side hypotheses (in-process scheduler, NCCL, OOM, step counter) are NOT applicable to STUS jobs; STUS-side hypotheses (upstream checkpoint feed, STUS-internal republish, GMPP backpressure) are NOT applicable to real trainers. Source: 2026-05-08 — same trap hit THREE times in one session: m2128360468 (S661157 STUS publish), m2125399403/m2125249288 (csanghera arms STUS), m2133142909 (this thread STUS) — bot kept proposing "in-process trainer scheduler stuck" hypotheses for jobs that have no training. | Hypothesis space wrong by half. "Trainer in-process scheduler stuck" / "trainer step counter drift" / "trainer didn't trigger FULL_SNAPSHOT" all FALSE on STUS jobs — those entirely live in different code paths. Operator chases the wrong layer; cross-team escalation goes to the wrong team (mvai vs silvertorch). |
| R15 | **Recurring-flow enablement check — verify `is_enabled` BEFORE blaming downstream symptoms** | When a "trainer not producing checkpoints" / "publish stalled" / "FULL_SNAPSHOT gap" symptom is found, BEFORE concluding the root cause is downstream (fire-app expired, fbpkg cleanup, in-process scheduler, GMPP backpressure, STUS internal skip), VERIFY the recurring flow that drives the trainer is enabled. **Procedure**: (1) From the served model id or trainer MAST job, find the recurring job id via `meta ai.workflow-run inputs --id=<workflow_run_id>` or by scanning the trainer's `application_metadata.flow_root_workflow_run_id`. (2) Run `meta ai.recurring-job recurring-flows --owner=<owner>` and locate the flow. (3) Check `is_enabled` column. **If `false` → THAT is the root cause; downstream symptoms (stale fire-app, no new instances, STUS skip log) are CONSEQUENCES, not causes.** Disabled flow → no recurring runs → no fresh fire-app rebuilds → old pin gets auto-deleted under `auto_delete_oldest` → trainer can't pull → no new training checkpoints → STUS correctly skips publish. The cascade looks like P17, but the root is upstream. Source: 2026-05-08 m2133142909 — bot diagnosed P17 (fire-app GONE) on root m2133154105, missed that recurring flow 8921769 (`threads_feed_esr_prod`, owner chengchengyuan) was `is_enabled: false`. Operator manually identified the disabled flow and corrected the diagnosis. | Bot proposes a fix recipe (rebuild fire-app, preserve, restart trainer) for a model the owner has DELIBERATELY decommissioned. Operator wastes time, model owner gets paged for a non-issue, real follow-up (was the disable intentional or accidental?) gets missed. |
| R16 | **Alert applicability check — verify the alert's expected snapshot types ACTUALLY APPLY to the model's class BEFORE investigating the symptom as real** | When an alert says "missing snapshot types X, Y, Z" (or any alert that asserts an expected output cadence on a model), the FIRST check is: does this model EVER produce X, Y, Z? **Procedure**: pull last N=2000+ instances for the model via `meta ai.model.instance list --model-id=<ID> --limit=2000 --sort-by=creation_time --sort-order=desc -o json`, group by `snapshot_type`, count occurrences. If ANY expected snapshot type has 0 occurrences in the lookback window, the alert is **misconfigured for this model class** — it's a FALSE ALARM, not a real failure. Standing hypothesis becomes "alert config error, requires per-model snapshot-type filter", NOT "publish path broken". Recommend re-tuning the alert (subtract the inapplicable type from the alert's expected-set) or re-classifying the alert as benign for this model class. Source: 2026-05-08 m2132070936 (`umia_hstu_online`, facebook_reels_ifu_i2i) — alert title "Publishing Stability ... missing snapshot types SPARSE_DELTA, DENSE_DELTA"; bot DID note "DENSE_DELTA never produced in 10k-instance lookback" as a sub-finding but failed to promote "alert is misconfigured" to the standing hypothesis. Drifted to FULL_SNAPSHOT investigation (different alert, different model) and the disabled-flow rabbit hole instead. Operator: "This is false alarm. The alert expect dense delta, which doesn't apply to this model. you failed to pinpoint the root cause." | Operator chases a non-issue. The bot publishes a fix recipe for a real failure that doesn't exist. Real fix (alert config tuning) gets buried as a sub-recommendation instead of THE answer. |
| R18 | **Diagnosed-stage scope re-check — the diagnosed root cause's pipeline stage MUST match the cron's lane scope BEFORE publish** | Org-scope ("this SEV is MRS-org") and stage-scope ("this SEV is OT-pipeline") are distinct. A SEV can be auto-tagged `mvai-online-training` because the model_id has training upstream, while the actual root cause lives in serving (T4: ICSP solver mode, RAAS, predictor config), publishing infra (T3: SilverTorch internals OUTSIDE the OT-publish path), or non-OT model lifecycle (Multifeed deploy plan, model launch gate). When triage IDs the root cause, run a final stage check before publishing the diagnosis. **Procedure**: after step (i) ground-truth verification confirms the standing hypothesis, classify the diagnosed root cause's pipeline stage (T1 ingestion / T2 training / T3 publishing / T4 serving / out-of-pipeline lifecycle). If diagnosed stage ≠ the cron's lane (mrs_online_training = T1–T3 OT pipeline), do NOT publish the OT-routed diagnosis; instead emit a single-line `out_of_scope: <stage>-stage SEV — routes to <correct_owner>` and silently drop. Tag-based routing is necessary but not sufficient: the diagnosed root cause is the authoritative scope signal. **Falsifier**: if the diagnosed stage IS T1/T2/T3 (DPP starvation, trainer hang, FS publish stall), publish normally. **Sources**: 2026-05-13 S661843 (`ig_stories_tray_mtml` holdout) — cron correctly diagnosed root cause as ICSP `solver_mode=ON_DEMAND` (T4 serving-stage failure), explicitly falsified training-path hypothesis A ("no `mvai-training-online-875799562` MAST job"), but published the diagnosis routed to mrs_online_training because the SEV was tagged `mvai-online-training`. Operator: "This is not an online training SEV. This is inference stage SEV. Right?" Mirrors the org-vs-stage scope conflation that R16 caught at the alert-applicability layer; R18 generalizes the principle to the diagnosed-root-cause layer. | Bot publishes a diagnosis on a SEV the OT oncall does not own; serving / RAAS / lifecycle owners get bypassed; OT lane gets noise volume that drowns real OT incidents; postmortem-fields stay missing because the actually-responsible team never sees the cron's diagnosis. Recurrence trips trust in the cron's auto-routing. |
| R17 | **Trainer-liveness probe BEFORE D-class (publish) or E-class (DPP/QPS) hypothesis** | When the symptom set includes ANY of: "snapshot stuck CREATING", "FS publish stalled", "missing SPARSE_DELTA/DENSE_DELTA", "DPP reader QPS ≈ 0", "low input QPS", "checkpoint cadence broken", run the trainer-Python liveness probe FIRST. **Procedure**: `meta scuba.dataset query -d mvai_metrics --view=samples --columns=time -w '[{"column":"model_entity_id","op":"eq","values":["<MODEL_ID>"]}]' --hours=12 -l 1 --order-by=time` pulls the latest sample timestamp emitted by trainer Python instrumentation. **If latest sample > 5 min stale AND MAST attempt status is RUNNING → the trainer Python interpreter is hung (P44/A1 GIL hang, or A2/A3 C++/storage stall depending on live process inspection); downstream stuck-CREATING snapshots and low DPP QPS are CONSEQUENCES, not roots.** Do NOT propose D-class (TGIF, Hedwig, UMM publish) or E-class (DPP starvation) hypotheses until A is falsified by a fresh mvai_metrics sample. Cite verbatim: `[VERIFIED: mvai_metrics latest_sample=<timestamp>, gap_min=<N>, attempt_status=<S>]`. To pinpoint hang onset, bucket samples: `meta scuba.dataset query -d mvai_metrics -a count -w '[{"column":"model_entity_id","op":"eq","values":["<MODEL_ID>"]}]' --hours=12 --time-bucket="30 minutes"` — sharp drop to 0 = hang onset window. Source: 2026-05-13 model 2135033479 (`facebook_reels_ifu_mtml_v0` IFU offline ranking prod, 4h 32m hang) AND model 883552231 (holdout, same model_type) — first triages BOTH misdiagnosed as TGIF/checkpoint_agent stuck (D-class) before the trainer GIL hang was identified via mvai_metrics zero-samples timeline. See `ot-failure-mode-catalog.md` § Cause-vs-consequence map and P44 in `known_patterns.md`. | Bot proposes D-class (publish-pipeline) or E-class (DPP-side) fix recipes for symptoms whose actual root is a CPU-side trainer hang. Operator chases publish/DPP team; correct owner (model owner + MVAI/pytorch oncall) is never paged. NCCL watchdog will NOT fire (CPU hang, no collective tripped) so the system never self-recovers. Misdiagnosis observed twice in one day on the same model_type. |
| R5b | **Cross-ref SEV that matches the symptom verbatim is the standing hypothesis** | Sibling clause to R5. When a cross-ref SEV's title or impact field matches the user-reported symptom verbatim (or near-verbatim), that cross-ref is the default standing hypothesis until falsified — do NOT elevate an inferred new hypothesis above it. Concrete: csanghera reported "poor source rate metrics for AMD arms"; cross-ref S661169 was titled "AMD snapshots rejected on AMD hardware"; the bot ranked an inferred "stalled training" above the verbatim match. Reordering the priority would have given the right answer first. | Inferred-but-novel hypotheses feel more specific and get elevated above already-open SEVs that exactly describe the symptom. Operator chases the wrong target. |

## Diagnosis output template

**Audience determines style.** When the bot posts to surfaces OUTSIDE this team space (`mrs.ot` Workplace group, SEV GChat space root, cross-team channels), use the **crisp 5-element template** — see [`crisp-report-style.md`](crisp-report-style.md). Verbose 9-section output goes to a paste linked from the post body. Crisp template: title + PROBLEM (1 sentence + 1-2 numbers) + LIKELY CAUSE (1 sentence + `path:line`) + paste link + ASK (1 sentence). Total ~6-7 lines.

The 9-section internal-debug template below is for in-thread replies WITHIN this team space, where the audience is already engaged debuggers.

Every output (interactive, cron, CLI) appends three sections after the standing hypothesis:

| Section | Format | Why |
|---|---|---|
| **Raw log Evidence** | Lettered blocks (A/B/C) of verbatim `[trainer0]:<line>` lines, each prefaced by a one-line claim. Hypothesis cites them inline: `NE stalled 22:03→22:40 [Evidence D, F]`. | Claim becomes un-fakeable once literal line is in the diagnosis. |
| **Investigation Commands** | Numbered replayable `meta` / `tw log` commands. Use `tw log` recipes from [`tw-log-recipes.md`](tw-log-recipes.md). | Diagnosis becomes a runbook, not a verdict. |
| **Files-touched table** | Path + 1-line role for every "fix in X" recommendation. | Reviewer + future-investigator navigation. |

## Signal-class taxonomy (per-cluster lane label)

Cluster notification prefixes carry a `signal_class` label, computed from the SEV title via `team_lane_scope.classify_signal_class()`. The label is NOT "`mrs_online_training` for everything in OT scope" — that conflates "this SEV is in the OT-coordination lane" with "this SEV is an online-training-path incident", and routes attention wrong.

| signal_class | Title regex (case-insensitive, first match wins) | Meaning |
|---|---|---|
| `mvai_publish_pipeline` | `cogwheel\|TGIF\|conveyor\|lowering\|XL_WEIGHTS\|publish(?!er)\|gmpp\|silvertorch\|light_cli\|fbpkg\|build[ _]node` | Publish/conveyor/release path — trunk publish blocked, lowering exception, snapshot delivery, release CLI / fbpkg build failures (S659092) |
| `mvai_serving` | `vanguard\|predictor\|serving_eval\|sigrid` | Serving/predictor side — vanguard fail, serving_eval, sigrid model manager |
| `mrs_online_training` | (default) | Actual training-path SEVs — sparse stream stopped, MAST job down, NaN NE, NCCL, OOM |

Cron renders the label literally in the notification prefix (e.g. `🚨 [OT SEV | mvai_publish_pipeline] L4 S<id>: ...`). Taxonomy + classifier live in `src/capabilities/team_lane_scope.py` (single source of truth); override at `team_lane_scope.signal_class_patterns`.

**Class-gated admission (post-classification).** After signal_class is computed, admission is gated on `team_lane_scope.signal_class_admit_allowlist` (default: `{mrs_online_training, mvai_publish_pipeline}`). A SEV that passes the upstream signal checks (tag / title / IC / owner / sev_type) but classifies as `mvai_serving` is dropped — inference-stage SEVs are MVAI-team scope, not OT-coordination scope. Source incident: S659181 (2026-05-05, `[mvai/...] sigrid predictor error rate`). To re-open the lane to serving SEVs, override yaml: `signal_class_admit_allowlist: [mrs_online_training, mvai_publish_pipeline, mvai_serving]`.

## Cluster discipline

N alerts/posts share root cause (same model id, same signal class, ≤10 min apart) → ONE diagnosis covering all. Cron clusters before diagnosing; manual triage follows the same rule.

## Try yourself before delegating

Before any "you should check X" / "please verify Y" line, run the 6-step gate. (Source: 2026-05-01 `wait_for_publish_completion` verification was delegated to user for ~2h; `mvai:mast-job-inspector` skill with `lg` recipe bypassing meta CLI OOM was available the whole time.)

| Step | Question | If yes |
|---|---|---|
| 1 | `meta` CLI subcommand for X? | run it |
| 2 | MCP tool (loaded or via ToolSearch)? | call it |
| 3 | fbcode capability function (`src/capabilities/`)? | invoke it |
| 4 | **Skill for X?** (most-missed step) | load via Skill tool |
| 5 | Manifold path? | read it |
| 6 | None worked? | document which ones tried + failure modes, THEN delegate |

Anti-pattern signal: more "you should check..." lines than "I checked X and got Y" lines → verification is being delegated.

## Stage-skill invocation (mandatory when symptom maps to a stage)

The agent MUST invoke the stage's skill before publishing the standing hypothesis. The dedicated skill exists precisely because the obvious read is often wrong. Authoritative copy of the mapping in `triage_config.py → CONFIG["stage_skills"]`:

| Stage | Sub-class | Symptom signature | Skill |
|---|---|---|---|
| T1 | Data Ingestion | DPP starvation, scribe lag, training example age, freshness regression | `fbcode/data_preproc/.llms/skills/dpp-online-training/SKILL.md` (entry; sibling `dpp-*` skills cover sub-symptoms) |
| T2 | Training | MAST job failure, NCCL/NaN/OOM, trainer stuck, app errors | `fbcode/minimal_viable_ai/agent/skills/mvai-ot/reliability/workflows/triage.md` (entry; broader `mvai-ot/reliability/` tree) |

## Two-number confidence (symptom vs root cause)

Single-number confidence conflates two questions. Always report both:

- **Symptom-attribution:** how sure is the failure in this stage / signal class? (Usually high — direct ground-truth queries.)
- **Root-cause:** how sure are we WHY? (Usually lower — hypothesis about trigger.)

Large spreads (e.g., symptom 85% / root-cause 20%) must be called out — high-symptom is actionable for routing, low-root-cause is a flag to keep digging. (Source: 2026-05-01 `ig_textpost_feed_m2m_retrieval` published "60%" — actually 85%/20%.)

## When you can stop

| Stop OK if | Don't stop if |
|---|---|
| External boundary (other team's code, off-machine service, foreign SEV) | Pattern matched at high confidence (still verify) |
| Concrete next-action requiring human decision | Cron's output looked plausible (cron output IS your input) |
| Standing hypothesis consistent with all ground-truth data | Alert assignee named (verify it's the right escalation) |
| | "Verifying takes longer" (deep triage takes time — that's the trade) |

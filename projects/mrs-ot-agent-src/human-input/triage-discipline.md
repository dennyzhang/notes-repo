**Pattern match is the OPENING of triage, not the conclusion.** Every caller (interactive Claude, `team_bot.py` cron, WIB bot @mention, manual CLI) must run the verification chain before publishing a diagnosis. Stopping at "P01 fired with 68% confidence" without ground-truth verification produces an unfalsified guess.

## Verification chain (required for every non-trivial triage)

1. **Pattern hypothesis.** Run keyword-and-signal pattern match against `known_patterns.md`. State leading + secondary candidates explicitly. This is your starting point, not your answer.

2. **Ground-truth verification — MUST cover BOTH publishing AND trainer state for any T3 alert.** A publishing alert is never just about publishing — trainer state distinguishes a real failure from a bootstrap artifact. Run ALL:
   - `meta ai.model.instance list --model-id=<ID> --limit=30 --sort-by=creation_time --sort-order=desc --columns=instance_id,creation_time,snapshot_type,state -o table` — snapshot timeline
   - `meta ai.mast-job metadata --name=<JOB>` — current version + state
   - `meta ai.mast-job attempts --name=<JOB> -o json` — attempt history
   - `meta ai.mast-job insights --name=<JOB> --version=<CURRENT> --attempt=<CURRENT_AT> -o json` — analyzer flags
   - `meta ai.mast-job error --name=<JOB> --version=<PREV> --no-truncate -o json` — **CRITICAL** verbatim error from PREVIOUS failed version. Without it you only see post-restart silence. Never trust upstream "RUNNING = healthy" without re-pulling. (Source: 2026-05-02, `ig_textpost_feed_m2m_retrieval` v32 DataClientStuckException at 21:21 PDT was missed for hours.)

   Each `known_patterns.md` row has a *Verification Check* column — run it. Examples: P01 (FULL_SNAPSHOT blocking deltas) → verify FULL_SNAPSHOT in gap window; P05 (Trainer OOM) → CUDA OOM in error AND `analyze-zoomer-memory` >90% (falsified if mem util <70%); P19 (NCCL from publish stall) → NCCL error AND temporal correlation with `gmpp` events.

2-b. **Timing-window reasoning.** State three timestamps in every diagnosis: (1) trigger event, (2) alert fire time, (3) SLO window (MAJOR=1.2× cycle_minutes, CRITICAL=3.0× — see `mvai-ot/reliability/operations/monitoring.md`). If the alert fired within ~1 SLO window of a fresh trainer restart, default explanation is "post-restart bootstrap" — not "infra broken". Skipping this step is a common over-attribution.

2-c. **Read SEV's live GChat — MANDATORY when a chat channel exists.** Live thread is newer than snapshot. Extract `gchat_space_url` / `chat_url` from metadata; if `communication_channel` is non-GChat or absent, note `[no live chat channel — metadata-only]` and skip. Otherwise run `gchat read <space_id>` for ~20 most recent messages, parse for active hypotheses, paste links, ETAs, and contradictions to `root_cause` / `remediation`. Cite per-fact: `[VERIFIED via gchat read <space_id>]`. (Source: 2026-05-02 S657811 — metadata said "archiver restarted, awaiting catchup"; GChat said "~150 versions need manual deletion, won't be solved till next week".)

2-d. **Read the reporter's linked artifacts + TRACE THE CONFIG/LAUNCH INTO SOURCE CODE — MANDATORY when the symptom is config/code/checkpoint-rooted OR the reporter links a paste/config/diff/file.** Do NOT triage off the post summary + MAST metadata alone — that is the #1 cause of a thin triage. (a) Read EVERY linked paste/config verbatim (runtime config `P####`, etc.). (b) Resolve the launch command's config FQNs (`--delta-publish-config-fqn`, `--*-config-fqn`) and the model's `trainer_config` into the ACTUAL fbcode source — code-search → read the file at `path:line`. (c) Compare against the SIBLING configs (same struct for other roles/models) — drift between siblings ("only this one was never updated") is a top root-cause class. (d) Output the EXACT fix as `path:line` + the diff hunk, not a vague "fix the config." Pattern-match is a *hypothesis*; for code-rooted symptoms the *answer* is in the source — read it. **DISPATCH (mandatory when the trace needs ≥1 source file or a sibling-config comparison):** do NOT attempt the multi-file source-trace inline under the cron's ~5min/post budget — dispatch a focused subagent via the Agent tool using the verbatim prompt at [`team_bot/references/deep-triage-subagent-prompt.md`](../team_bot/references/deep-triage-subagent-prompt.md), then fold its ROOT CAUSE + FIX + `🧠 Context` into the diagnosis. Same lane as the diff-subagent — a dedicated subagent has the budget the inline cron path lacks. (Source: 2026-06-04 `EOXLCWrOWZM` — cron triage of post 1342971631130913 / Threads ESR `2121486280` restart-loop was thin: it pattern-matched off the post + MAST metadata and paged, never reading the reporter's runtime-config paste nor tracing `ESR_OT_DELTA_UPDATE_PUBLISH_CONFIG` → `ESR_WEIGHT_DELTA_PUBLISH` in `feed/conf/delta_publish_configs.py`, whose hardcoded `skip_embedding_table_names` *looked* like it was missing 3 RES tables — the bot's code-trace **hypothesis**. **CORRECTION (verified from the incident archive): the model owner later confirmed a DIFFERENT model-side config root cause** (fixed via D107578770); the skip-tables trace was wrong. So even a confident source-trace is a hypothesis — **confirm root cause with the owner before canonizing it.** (The trace-into-source lesson still holds vs pattern-matching off the post; just don't treat the trace's first answer as ground truth.) The cron skipped the source-trace; this step closes that gap, and the `🧠 Context:` line will show `code ✗` when it's skipped.)

3. **Active-SEV cross-reference.** Run `meta sevmanager.sev list --in-progress --created-after="2 days ago" --columns=sev_number,title,sev_type,status -o json`. Cross-org Scribe / Hedwig / DPP infra SEVs often won't carry the OT tag but ARE the upstream cause. For each open SEV with adjacent signal class, surface the SEV id and connection. Don't assume the alert is isolated.

4. **Owner correction — model owner is PRIMARY, system-fix owner is SEPARATE follow-up.** Run `meta ai.model-series metadata --model-id=<MODEL_ID>` for `owner_unixname` and `oncall`. Diagnosis "Owners":
   - **Primary (this incident):** model `owner_unixname` + model oncall + product oncall (e.g., `p92_relevance_retrieval_oncall`).
   - **Source owner:** literal `assigned_user` (alerts) / `owner_unixname` (SEVs) from upstream JSON.
   - **OT-side escalation:** per-product routing from `team_bot_config.yaml`.
   - **Secondary follow-up (only if a system bug exists):** owner of any routing/config bug surfaced.

   Don't promote a system-bug fixer to primary just because they show up in fbcode commits. (Source: 2026-05-02 `ig_textpost_feed_m2m_retrieval` triage suggested lupaul as primary instead of model-owner ronghuang.)

5. **Hypothesis chain.** Take the leading pattern, test against (2). If contradicted, *write the falsification* and switch to the secondary. Standing hypothesis is the one surviving verification — not the highest-confidence pattern match.

## Per-fact tagging — VERIFIED vs INFERRED

Every load-bearing claim carries one of two markers:

| Marker | Means | Example |
|---|---|---|
| `[VERIFIED]` | Sourced from `meta` CLI / Scuba / capability output. Exact command must appear in Evidence Package. | `MAST v32 died 21:21 PDT [VERIFIED via meta ai.mast-job error --version=32]` |
| `[INFERRED, NOT PROVEN]` | Hypothesis from pattern-match / correlation / analogy. Not confirmed by direct data. | `S658056 is upstream cause [INFERRED — needs timeline correlation]` |

A real-incident diagnosis with no markers of either kind is wrong — both should appear. (Source: 2026-05-02 `ig_textpost_feed_m2m_retrieval` asserted "delta-only, never FULL_SNAPSHOT" at 80% confidence based on a single anomalous query; explicit `[INFERRED]` tagging would have surfaced over-confidence.)

| # | Rule | Mandate | Failure mode without it |
|---|---|---|---|
| R1 | **Baseline before anomaly** | Cite same job/metric in known-good window before claiming "broken/slow". Ex: "publish 42 min — earlier cycle 4 min". | Reader can't tell 42 min from normal. |
| R2 | **Layered hypothesis enumeration** | Enumerate every layer the symptom could live at, rule each in/out. No single-hypothesis. Ex: "BD writer 1.6 GB/s NOT bottleneck; Hedwig 2-26 MB/s IS." | Guess masquerading as diagnosis. |
| R3 | **Code-pointer on recommendations** | Every "fix X" cites file path + line. Ex: `trainer_config.py:618-633`. | 5-min file hunt to act. |
| R4 | **Tiered recommendations** | SHORT (≤1d, config flip/revert/JK); MEDIUM (≤1w, cross-team); LONG (weeks+, refactor). | "Async refactor" weighted same as "bump value". |
| R5 | **Soft cross-refs include verification** | Next-action MUST include verification command BEFORE any contingent fix. NOT "if X is upstream, do Y"; instead "first run Z to verify; if yes, then Y". | Soft refs promoted to action items on wrong premises. (Source: 2026-05-02 S657811→S658142.) |
| R6 | **Temporal consistency on suspect diffs** | SEV `first_occurrence_time` ≥ X's land time before naming X as regression source. Pull occurrences explicitly. | First-occurrence pre-dates the diff → at most amplifier, not trigger. |
| R7 | **Frequency-over-time inflection check** | For multi-day SEVs, plot occurrence frequency. Step-change → check diffs near inflection. | "Soft-warn → hard exception" pattern: latent gap tolerated for days, then a validator diff converts warn to exception. |
| R8 | **Entity multiplicity rule** | Pull SEV's full entity list before forming entity-specific hypothesis. Single → likely entity-specific config; multiple → systemic. | Per-entity fixes chased on systemic problem. |
| R9 | **Mechanism over conclusion** | When the diagnosis is a misconfig, perf regression, or resource exhaustion, name the data-flow chain (Phase A → Phase B → ...) and identify which phase the symptom emerges in. Ex: "delta publish has Phase 1 GPU (`delta_tracker.get_unique → torch.topk → GPU→CPU copy`, blocks training) and Phase 2 CPU async (Hedwig publish backlog). The CPU OOM comes from Phase 2 backlog, not Phase 1 selection mode." | Reader sees "X causes Y" without understanding *how*, can't extrapolate the fix to a sibling case, can't tell which knobs are mechanism-relevant vs cosmetic. |
| R10 | **Calibration anchors on numeric fix recs** | Every numeric knob change cites (a) typical safe value across the fleet AND (b) safe value for the offender's class. Ex: "Reduce `embedding_delta_percentage` to 25-50% (current 100%). Most models use 25% for non-critical tables, up to 100% only for user ID tables." Also cite preconditions when applicable: "Enable concurrent delta — but check memory headroom first (need ≥20% free during full publish)." | "Reduce X" without anchors makes the operator guess; under-tuning leaves the issue, over-tuning creates a new one. |
| R11 | **Root model vs served model — distinguish in every snapshot/staleness diagnosis** | When the symptom is on a served model id (snapshot stall, model age growing, deployment lag), the root cause may be on the upstream root training model id, not the served id. Every diagnosis MUST cite BOTH ids when they differ: `served_model_id=<X>, root_training_model_id=<Y>`. Before naming a fix, walk the lineage to confirm which side the failure lives on (TMS state, MAST job state, fbpkg expiration are root-side; serving errors, predictor age are served-side). Source: 2026-05-08 S661157 — original P38 attribution to served `m2128360468` was wrong; root cause was P17 on root training `m2131533016` (fire-app fbpkg expired). Conflating the two cost ~6h of misdirected diagnosis. | Diagnosis chases the wrong model id; fix proposed on serving side when root cause is upstream training; "snapshot stall" labeled as `Boxcar preemption` when it was `fbpkg expired`. |
| R12 | **Verify model_id ↔ MAST job linkage before connecting them** | Before reasoning "MAST job X is causing model Y's symptom", grep the MAST job's `application_metadata.flow_root_workflow_run_id` AND `model_entity_id` fields and confirm they match Y. Two facts adjacent in time on the same dashboard are NOT necessarily causally linked. Source: 2026-05-08 csanghera Workplace post triage — bot joined "MAST f1078664497 long-running" + "snapshots stale on m2125399403/m2125249288" into one hypothesis, but the MAST job actually wrote to m2125436031 (a different model). Validator caught it. | Two coincidentally-stale facts get welded into a fake causal chain; the real upstream (e.g. an open SEV) gets ranked secondary because the inferred chain feels more specific. |
| R13 | **Long-running ≠ stalled — require step-rate / progress signal** | "Job is 3x baseline duration" is NOT evidence of stuck. A run can take 3x longer for legitimate reasons (data shape, capacity, retries) and still complete cleanly. Before claiming a job is stalled, cite (a) trainer step rate / TensorBoard progress signal showing flatline, OR (b) a fresh `meta ai.workflow-run status` that the run actually ended in non-success state, OR (c) trainer logs showing no-op for >Nx the typical step interval. "no end_time" in cached metadata is NOT the same as "stalled". Source: 2026-05-08 csanghera triage — bot inferred f1078664497 was stalled at 19h vs 6h baseline; validator re-queried and found the run had completed at 13:48 PT (~19.4h, SUCCEEDED). | False alarms route operator attention to a job that is fine; misses the real signal (a cross-ref SEV that directly matches the symptom). |
| R14 | **Job-role verification — check `entrypoint` BEFORE assuming `mvai-training-online-<id>` is a trainer** | The MAST naming convention `mvai-training-online-<MODEL_ID>` is shared by **two distinct job classes**: (1) actual training jobs whose entrypoint is `train.py` / `mvai-train` / equivalent, and (2) SilverTorch update service (STUS) publish jobs whose entrypoint is `silvertorch/experimental/st_update_service/st_update_service.py`. STUS jobs do NOT train — they consume upstream root checkpoints and republish. **Before forming any "trainer is stuck / publishing / scheduler" hypothesis, run `meta ai.mast-job metadata --name=mvai-training-online-<id>` and grep `entrypoint`.** Branch the hypothesis space accordingly: trainer-side hypotheses (in-process scheduler, NCCL, OOM, step counter) are NOT applicable to STUS jobs; STUS-side hypotheses (upstream checkpoint feed, STUS-internal republish, GMPP backpressure) are NOT applicable to real trainers. Source: 2026-05-08 — same trap hit THREE times in one session: m2128360468 (S661157 STUS publish), m2125399403/m2125249288 (csanghera arms STUS), m2133142909 (this thread STUS) — bot kept proposing "in-process trainer scheduler stuck" hypotheses for jobs that have no training. | Hypothesis space wrong by half. "Trainer in-process scheduler stuck" / "trainer step counter drift" / "trainer didn't trigger FULL_SNAPSHOT" all FALSE on STUS jobs — those entirely live in different code paths. Operator chases the wrong layer; cross-team escalation goes to the wrong team (mvai vs silvertorch). |
| R15 | **Recurring-flow enablement check — verify `is_enabled` BEFORE blaming downstream symptoms** | When a "trainer not producing checkpoints" / "publish stalled" / "FULL_SNAPSHOT gap" symptom is found, BEFORE concluding the root cause is downstream (fire-app expired, fbpkg cleanup, in-process scheduler, GMPP backpressure, STUS internal skip), VERIFY the recurring flow that drives the trainer is enabled. **Procedure**: (1) From the served model id or trainer MAST job, find the recurring job id via `meta ai.workflow-run inputs --id=<workflow_run_id>` or by scanning the trainer's `application_metadata.flow_root_workflow_run_id`. (2) Run `meta ai.recurring-job recurring-flows --owner=<owner>` and locate the flow. (3) Check `is_enabled` column. **If `false` → THAT is the root cause; downstream symptoms (stale fire-app, no new instances, STUS skip log) are CONSEQUENCES, not causes.** Disabled flow → no recurring runs → no fresh fire-app rebuilds → old pin gets auto-deleted under `auto_delete_oldest` → trainer can't pull → no new training checkpoints → STUS correctly skips publish. The cascade looks like P17, but the root is upstream. Source: 2026-05-08 m2133142909 — bot diagnosed P17 (fire-app GONE) on root m2133154105, missed that recurring flow 8921769 (`threads_feed_esr_prod`, owner chengchengyuan) was `is_enabled: false`. | R16 | **Alert applicability check — verify the alert's expected snapshot types ACTUALLY APPLY to the model's class BEFORE investigating the symptom as real** | When an alert says "missing snapshot types X, Y, Z" (or any alert that asserts an expected output cadence on a model), the FIRST check is: does this model EVER produce X, Y, Z? **Procedure**: pull last N=2000+ instances for the model via `meta ai.model.instance list --model-id=<ID> --limit=2000 --sort-by=creation_time --sort-order=desc -o json`, group by `snapshot_type`, count occurrences. If ANY expected snapshot type has 0 occurrences in the lookback window, the alert is **misconfigured for this model class** — it's a FALSE ALARM, not a real failure. Standing hypothesis becomes "alert config error, requires per-model snapshot-type filter", NOT "publish path broken". Recommend re-tuning the alert (subtract the inapplicable type from the alert's expected-set) or re-classifying the alert as benign for this model class. **THRESHOLD_MISFIT subcases (when snapshot-type check passes but alert still fires):** (A) *Retired/decommissioned model* — `meta ai.mast-job metadata --name=mvai-training-online-<id>` shows DEAD/KILLED state with no recent checkpoints → THRESHOLD_MISFIT/RETIRED_MODEL: NO_ACTION + file T-task to DISABLE the detector (not tune threshold — model won't produce new snapshots regardless of threshold). Pattern: T275008531 (ALERT-901863119115094, ig_reels_tab_vm_esr 2141728943, threshold ~90min vs. actual ~185min cadence). **Falsifiers:** (A) MAST job is RUNNING → not retired → fall through to P50/P04 publish-pipeline triage. (B) actual_interval ≤ threshold → threshold correct → real publish failure; triage as P50/P04. **Validation-evidence (2026-06-12, ot-knowledge-distillation):** 2 confirmed THRESHOLD_MISFIT FULL_SNAPSHOT cases (distinct subcases A + B) in the 2026-06-10/2026-06-12 corpus. | R18 | **Diagnosed-stage scope re-check — the diagnosed root cause's pipeline stage MUST match the cron's lane scope BEFORE publish** | Org-scope ("this SEV is MRS-org") and stage-scope ("this SEV is OT-pipeline") are distinct. A SEV can be auto-tagged `mvai-online-training` because the model_id has training upstream, while the actual root cause lives in serving (T4: ICSP solver mode, RAAS, predictor config), publishing infra (T3: SilverTorch internals OUTSIDE the OT-publish path), or non-OT model lifecycle (Multifeed deploy plan, model launch gate). Tag-based routing is necessary but not sufficient: the diagnosed root cause is the authoritative scope signal. **Falsifier**: if the diagnosed stage IS T1/T2/T3 (DPP starvation, trainer hang, FS publish stall), publish normally. **Sources**: 2026-05-13 S661843 (`ig_stories_tray_mtml` holdout) — cron correctly diagnosed root cause as ICSP `solver_mode=ON_DEMAND` (T4 serving-stage failure), explicitly falsified training-path hypothesis A ("no `mvai-training-online-875799562` MAST job"), but published the diagnosis routed to mrs_online_training because the SEV was tagged `mvai-online-training`. | R17 | **Trainer-liveness probe BEFORE D-class (publish) or E-class (DPP/QPS) hypothesis** | When the symptom set includes ANY of: "snapshot stuck CREATING", "FS publish stalled", "missing SPARSE_DELTA/DENSE_DELTA", "DPP reader QPS ≈ 0", "low input QPS", "checkpoint cadence broken", run the trainer-Python liveness probe FIRST. **Procedure**: `meta scuba.dataset query -d mvai_metrics --view=samples --columns=time -w '[{"column":"model_entity_id","op":"eq","values":["<MODEL_ID>"]}]' --hours=12 -l 1 --order-by=time` pulls the latest sample timestamp emitted by trainer Python instrumentation. **If latest sample > 5 min stale AND MAST attempt status is RUNNING → the trainer Python interpreter is hung (P44/A1 GIL hang, or A2/A3 C++/storage stall depending on live process inspection); downstream stuck-CREATING snapshots and low DPP QPS are CONSEQUENCES, not roots.** Do NOT propose D-class (TGIF, Hedwig, UMM publish) or E-class (DPP starvation) hypotheses until A is falsified by a fresh mvai_metrics sample. To pinpoint hang onset, bucket samples: `meta scuba.dataset query -d mvai_metrics -a count -w '[{"column":"model_entity_id","op":"eq","values":["<MODEL_ID>"]}]' --hours=12 --time-bucket="30 minutes"` — sharp drop to 0 = hang onset window. | R5b | **Cross-ref SEV that matches the symptom verbatim is the standing hypothesis** | Sibling clause to R5. ## Two-number confidence (symptom vs root cause)

Single-number confidence conflates two questions. Always report both:

- **Symptom-attribution:** how sure is the failure in this stage / signal class? (Usually high — direct ground-truth queries.)
- **Root-cause:** how sure are we WHY? (Usually lower — hypothesis about trigger.)

Large spreads (e.g., symptom 85% / root-cause 20%) must be called out — high-symptom is actionable for routing, low-root-cause is a flag to keep digging. (Source: 2026-05-01 `ig_textpost_feed_m2m_retrieval` published "60%" — actually 85%/20%.)

## Anti-laziness — proof-of-work gates confidence (the root of thin triage)

Agent laziness = **satisficing**: emit a *plausible* verdict for the least work,
stop at the first pattern match, page, done. It's invisible because a thin triage
*looks* complete. "Try harder" prose doesn't fix it (it gets skipped under task
focus). The structural antidote: **a verdict's confidence — and the right to PAGE —
must be EARNED by the evidence artifact its symptom class requires, present verbatim
in the diagnosis. No artifact → the deep work wasn't done → confidence is capped and
the verdict downgrades.** This makes laziness *mechanically detectable* (the validator
checks for the artifact), not a matter of willpower.

| Symptom class | Required proof-of-work artifact — else confidence capped ≤0.5, verdict → MONITOR + "needs deeper investigation" |
|---|---|
| config / code / checkpoint-rooted | verbatim SOURCE quote `path:line` + sibling-config comparison (via deep-triage subagent, step 2-d). "The config is wrong" with no source line = NOT done. |
| any PAGE verdict | verbatim prev-version MAST error (`meta ai.mast-job error --version=<prev> --no-truncate`) — never page on post-restart silence or metadata alone. |
| zombie / QPS→0 / hang | the OBSERVE probe-set results (mvai_metrics emission gap + GPU-mem), per `mast-debugging.md` Fact-Gathering catalog. |
| recurrence / family claim | the 4-source recurrence check + sibling sweep (R20/R21) output. |
| publishing (FS / delta) | snapshot timeline + trainer-liveness probe (cause-vs-consequence; never page a consequence). |
| **UPSTREAM_INFRA @ high confidence** | a `[VERIFIED]` metric that CONFIRMS the link — the upstream cause actively degrading the SPECIFIC dependency this model consumes, in the symptom window (the upstream SEV's own impact metric, the TMS BlockPlan / kill record CITING that SEV, or the resource's throttle/quota counter). "An upstream SEV exists + a similar symptom" = `[INFERRED]`, **NOT** high → cap at medium. **If the confirming metric does not exist, IDENTIFY + BUILD it** (a new scan / probe / decisive-metric query, per P-017) so the link is verifiable next time; confidence stays capped until it is. UPSTREAM_INFRA is not a free escape hatch — an unconfirmed "blame upstream" can mask a real in-lane failure. **And the `*Next actions*` must be SUBSTANTIVE, never a passive "monitor for expiry":** (a) build/cite the confirming metric above; (b) drive/track the upstream SEV — cite it, state whether it is progressing, escalate if stalled; (c) file the P-017 decisive-metric task if recurring. (2026-06-12 thread `e78lVJptOAI`: 880283513 was UPSTREAM_INFRA/high on an inferred SEV link AND its next-actions were thin — both gaps.) **Concrete confirming query — scribe-quota (CL-003/P57) class is now BUILT:** `tools/confirm-upstream-scribe.sh --model <EID> [--sev-tenant <tenant>]` → CONFIRMED (Scuba `mast_admission_control_decisions` shows `rejected=1`/`policy_name=ONLINE_TRAINING_SCRIBE_USAGE` for this model's job → throttling of THIS model is `[VERIFIED]`, high confidence earned) vs REFUTED (model runs on a different tenant / was never quota-rejected → cap to `[INFERRED]`/medium, look in-lane). - **Confidence is a function of evidence, not pattern-strength.** A strong pattern match
  with no artifact = symptom-confidence high / **root-cause confidence LOW** → MONITOR
  and keep digging (or dispatch the subagent) — never a high-confidence PAGE.
- **Missing artifact = "incomplete," not "low confidence."** Either gather it (dispatch
  the step-2-d subagent) or render MONITOR + "needs deeper investigation: <artifact not
  gathered>". Do NOT page a thin verdict.
- **External-attribution is CLASS-AGNOSTIC — this is the RCA for why shallow verdicts keep escaping (2026-06-13).** The table above enumerates classes, but rows were added REACTIVELY (one per operator-caught miss), so every NEW shallow-verdict class escaped until the operator pushed. UPSTREAM_INFRA was the live blind spot: no row → a high-confidence "blame the SEV" required no artifact and the validator had nothing to check → the bot satisficed at the shallow coexistence verdict. **Generalize, don't wait for a per-class row:** ANY high-confidence verdict whose root-cause is an EXTERNAL attribution — an upstream SEV, an upstream service (Scribe/ZippyDB/TMS/Manifold/…), or another team's code — REQUIRES a `[VERIFIED]` metric linking that cause to THIS entity's symptom (right scope/tenant + right window), regardless of whether its class has its own row. If the linking query does not exist, BUILD it (P-017) — then it becomes the class's artifact. The default for "it's caused by <external thing>" is: confirm the link, or cap to `[INFERRED]`/MONITOR and dig.
- **The validator enforces it** (it is now a laziness-detector, not just a correctness
  check): every pass asserts the diagnosis carries its symptom-class artifact and that
  the artifact actually supports the verdict; else `⚠ Validator: SHALLOW — <artifact>
  missing for a <verdict> verdict → downgrade + dig`. Cross-model codex pass for
  code-bearing triages. The `🧠 Context:` line is the cheap tell — `code ✗` on a
  config-rooted PAGE is a self-reported laziness flag.

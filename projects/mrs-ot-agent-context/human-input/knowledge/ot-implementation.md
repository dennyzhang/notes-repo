## MVAI Platform (training framework)

### How it works

MVAI is the training framework behind MRS/IG online-training (OT) jobs (`mvai-training-online-<model_id>`). Jobs are submitted to MAST via the **fire** CLI, which builds a launch quickapp request, registers the job in **TMS** (Training Management System), and on recurring jobs may transition recurring→adhoc and run post-launch cleanup (D106588525). Code ships in two packages: a **base layer** (`light_cli` and arch variants) carrying shared infra, and an **app layer** (`fire-app`/`mvai_app_*`) carrying model/overlay code. The decisive axis for *which layer a fix lands in* is overlay-PATH membership — paths in `PRESERVED_INFRA_CODE` are force-stripped from the app overlay, so they belong to base; package-name labels and build dates answer a different question and mislead (D108045383). App-layer fbpkgs carry retention/expiry (fire expires the app pkg `4w`, D106710214).

The shared `RecTrainer`/`trainer.py` runs `_train_impl` (per-epoch: dataloader+iterator creation, freeze params, then `_train_loop`). The **ETT event-logging** subsystem (`MVAITrainingEventsLogger.log_event`, `mvai_training_events_logger.py`) emits START/SUCCESS/FAILURE events to a Scuba table, keyed by `MVAIComponent` (TRAIN_LOOP, EVAL_LOOP, PRE_TRAIN, POST_EVAL, TRAINER, N_BATCHES_CALLBACK). Per-batch logging wraps `_before/_after_train_pipeline_progress` with an `event_sequence_id`, plus a one-shot `FIRST_N_BATCHES_EVENT_NAME` at `itrn==0` (D106832890, D107568603). The same `_train_loop` serves eval, so component selection is dynamic on `job_stage` (D105452012). This mirrors the PyPer/APF event patterns it was modeled on (D108396022, D108029151).

**Prod validation:** `OverrideProdValidator` queries TMS status/config before letting a job override prod (D108382499). **Recovery:** `mvai ban-versions` marks checkpoints/snapshots INVALID in **UMM**; `mvai online-training-mgr -c` clears per-job `info.json` from manifold (D108480297, D108489881).

### Recurring failure modes

- **Banned-checkpoint restart loop:** banning only set UMM INVALID without resetting `retryable_job_checkpoint_version` in the job `info.json` cache, so OT restarted from a banned checkpoint during SEV recovery (S675130/S675238, D108489881). The clear path also deleted `info.json` unrecoverably (D108480297).
- **Unmatched START events:** an exception between START and SUCCESS left a dangling START with no SUCCESS/FAILURE in Scuba; fix adds try/except FAILURE logging and SIGTERM flush via `MVAIShutdownHandler` (D108029151, D105291160).
- **Validation gaps:** `OverrideProdValidator` caught only narrow TMS/Thrift exceptions, propagating unexpected types instead of safely skipping override (D108382499).
- **`--dry-run` not respected:** TMS registration and `fbpkg expire 4w` ran even under `fire --dry-run`, silently mutating prod (D106588525, D106710214).
- **Zombie/stuck jobs:** elastic-agent error path hung on non-daemon threads (10.5h zombie, S665478); D2H copy on the training stream deadlocked against pending NCCL (D105606893, D105605650); `[MVAI_EXIT]` markers added to route zombie SEVs (D107459272).
- **Lifecycle mis-state:** user-killed jobs showed RUNNING not DEAD due to `IGNORED_OT_FAILURE_TYPES` filtering (D107310446); soft-expired leases mis-logged at ERROR (D107448117).

### Key knobs & design decisions

`fire --dry-run` (guarded); `fire -j <hosts>x<gpus>`; `max_app_retries` with OT defaults (prod-OT reset logic removed, D106566401); `OverrideProdValidator` broad-except fail-safe; `MVAIComponent` enum as the event taxonomy; `mvai ban-versions` + `info.json` cache reset as the canonical Revert-&-Ban recovery; HW pinning over `TC_ANY` to avoid QPS regression (D107110125). Base-vs-app layer routing is governed by `PRESERVED_INFRA_CODE` overlay membership, not package labels (D108045383).

## Checkpoint / TMS & Training Infra

### Checkpoint & TMS — how it works

An OT job persists a checkpoint pointer in retry state (`training_checkpoint_version`). The special value **`-1` is the "latest" sentinel** — it tells the loader to resolve to the most recent checkpoint via the model's **Parent checkpoint-lineage root** rather than naming an explicit version (D108525530). Critically, the model store treats only `version=None` as "latest"; a literal `-1` is looked up as if it were a real version number, so the resolution must happen *before* the store call or it raises `ModelStoreDBRecordNotFound: Checkpoint <eid> : -1 does not exist` (D108525530, D108539042). The hardened base job resolver detects the `-1` sentinel on the resume path, mirrors the loader's lineage resolution, and converts the record-not-found into an actionable error (D108538796, D108539042).

**TMS registration** is the OT register/start critical path: a sequence of state-mutating calls — `register / update / start / unexpire / set_training_state` — against TMS (a dependent service) (D108348708). Models carry registry metadata: `uses_online_training`, `criticality_override` tier, and product-group (PG) routing, all set in the MRS Model Registry; alerting thresholds are wired per-model (D106717796, D106424673, D106719175). Teacher models (e.g. VideoFM for DAS/KD) register OT without serving inference directly — downstream consumes their checkpoints (D106717796). Post-launch lifecycle has explicit transitions: `maybe_transition_recurring_to_adhoc_online` and `online_training_post_launch_cleanup`, which support a `dry_run` mode (D106623230).

**info.json — checkpoint-state resume pointer.** The file `deep_retrieval/tree/jobs/mvai-training-online-{model_id}/info.json` is a Manifold-persisted resume pointer that survives MAST restarts. It stores ONLY checkpoint state (version, model entity ID, epoch, reason) — NOT package versions. Package versions (`--app`/`--base`) are baked into the MAST job definition at submission time and frozen there. Two distinct restart paths exist: (A) **MAST-level retry** (same job, new task attempt) — reuses the frozen MAST job definition, same package version; (B) **fresh TLS launch** (new MAST job submission via TMS reconciler) — TLS calls `get_online_training_config()` which reads `aiplatform/training_launch_service/models/{model_id}` fresh from Configerator (`online_training_config_utils.py:32-33`), picks up any config changes including package bumps. S675860 root cause: v25 exhausted MAST retries (path A) all using frozen 1805 package; fix required: (1) land Configerator update to 2138 (D107809925), (2) clear info.json (`mvai online-training-mgr -c`) to reset checkpoint pointer, (3) `mvai online-training-mgr -m <id> -s online` — sets TMS ONLINE_READY, triggers TMS reconciler to include model in `to_start`, TLS then reads fresh Configerator and submits new MAST job with 2138. Note: `-s online` does NOT kill the running job (only calls `tms_helper.start_training_job()` = state change); if a job is still running, the new config is only picked up after that job dies. Divergence between current Configerator config and live MAST job visible via `mvai online-training-mgr diff-fire-args -m <model_id>`. The canonical schema (standard MVAI OT path):

```json
{
    "retryable_job_save_model_entity_id": <int>,
    "retryable_job_checkpoint_version": <int>,   // -1 = resolve via UMM (latest valid)
    "epoch": <int>,
    "reason": "<preemption|train completed|in train loop publish|retryable error recovery|...>"
}
```

Optional fields: `root_model_checkpoint_version` (U2I/teacher-student), `retryable_eval_job_checkpoint_version` + `eval_reason` (train-eval jobs).

**Two creation paths — key name divergence is the root of the ban bypass:**

Standard MVAI OT (`trainer.py`) calls `save_retryable_job_info()` (`core/utils/utils.py`) — the canonical wrapper that enforces key names. First write at `__init__` with `cp_version=-1, epoch=-1, reason=INITIALIZATION` when no prior job info exists. Every checkpoint save thereafter calls this same wrapper.

IFR trainer (`mtml/ifr/train.py`) bypasses the wrapper and calls `job.save_job_info()` directly with its own keys — only written after first checkpoint save (no initialization write). Both paths call `job.save_job_info()` (full overwrite), but with different key names:

| Path | Key written | Ban reset touches it? |
|---|---|---|
| Standard (`save_retryable_job_info`) | `"retryable_job_checkpoint_version"` | Yes — `reset_job_info_cache_checkpoint_version()` patches this key to -1 |
| IFR (direct `job.save_job_info`) | `"checkpoint_version"` | **No** — ban reset has no knowledge of this key |
| MTML training_helper | `"failure_recovery_checkpoint_version"` | No |

Fix options: (a) make IFR call `save_retryable_job_info` (adopt standard wrapper), or (b) make `reset_job_info_cache_checkpoint_version` reset both keys. The gap is structural — `save_retryable_job_info` exists precisely to standardize key names but IFR never adopted it.

Lifecycle: created on first checkpoint save; updated every subsequent checkpoint save; read on every MAST restart; patched to `-1` by `reset_job_info_cache_checkpoint_version()` after a ban; fully deleted by `mvai online-training-mgr -c` (backs up as `.{epoch}.bak` first — D108480297). Deleting vs patching to `-1`: deletion causes "first attempt" path (epoch counter resets, risk of new model entity ID registration); patching to `-1` preserves model identity and routes through UMM ban check. S675860 (2026-06-14, model 882278521): pkg 1805 deleted by auto_delete_oldest 6 min after protective tag removed; 20 MAST retries (path A) all used frozen 1805 job definition → exit code 7; fix = D107809925 (Configerator → 2138) + clear info.json + `-s online` (triggers fresh TLS launch reading Configerator → 2138 → v26 RUNNING). No Thrift schema — `mvai_infra/common/job.py` stores a raw `Dict`; schema is implicit per-caller only.

### MAST version vs MAST attempt — critical distinction for OT

Every OT job has two nested counters visible in MLHub URLs (`?version=25&job_attempt=0`):

**MAST version** — a new job submission created by TMS. Increments each time TMS stop+start fires: TLS calls `get_online_training_config()` which reads live Configerator (`aiplatform/training_launch_service/models/{model_id}`) and submits a new MAST job with the current `--app`/`--base`/command_arguments. Config changes (package bumps, locality constraints) are only picked up on a new version. Inspect with `mast get-job-definition <job> --version <N>`.

**MAST attempt** (`job_attempt`) — an in-version retry triggered automatically by MAST when a task exits with a retryable error. Uses the **same frozen job definition** as the version — same package, same command args, no Configerator re-read. Capped by `max_app_retries` (JustKnobs `minimal_viable_ai/fire:default_ot_max_app_retries` = **3** for OT; `minimal_viable_ai/fire:default_max_app_retries` = **2** for offline; user can override via `--max-app-retries`, capped at default; `-1` infinite retries blocked — `fire_impl.py:get_max_app_retries`).

```
v25 (version)
  └─ attempt 0: package fetch fails (exit 7, retryable) → retry
  └─ attempt 1: same → retry
  └─ attempt 2: same → retry
  └─ attempt 3: same → DEAD (exhausted max_app_retries=3)
v26 (new version — TMS fires after v25 dead)
  └─ TLS reads Configerator → picks up new config → success
```

**Package-not-found is retryable at MAST task level** — exit code 7 is classified as a retryable application error. The job burns through all `max_app_retries` attempts (~30 min each) before the version goes DEAD. This is a known gap: missing-package errors are deterministic and should be non-retryable to fail fast. TMS's launch-failure monitor (`training_platform_model_events`, `LAUNCH_TRAINING_RUN_STANDALONE_PACKAGE_NOT_FOUND`) is the backstop at the launch-request layer, but does not short-circuit in-version MAST retries. S675860 (model 882278521, pkg 1805 deleted): each attempt exited code 7, burned max attempts before v25 died and v26 (with pkg 2138 from Configerator) could start.

**TMS skills:** `/data/users/dennyzhang/fbsource/fbcode/ai_infra/training_management_system/.claude/skills/` — `training-debug` (router), `diagnose-launch`, `diagnose-package`, `training-ops` (restart/pause/resume reference), `model-status`.

### Training infra — how it works

Mechanism detail is **largely underspecified in this corpus**. Concrete signals: a non-NCCL stuck-job mode where **rank N hits SIGSEGV and the elastic-agent goes into D-state (uninterruptible sleep)**, hanging the job until manually killed — distinct from a Python-GIL hang and recurring on the same model (D106556357). RE (remote-execution) lowering workers can crash without a structured exception — SIGABRT from storage timeout or OOM — making transient-vs-deterministic ambiguous (D106022976). DPP variance is a triage red herring to *rule out* before blaming the trainer (D106114988). NCCL collective/missing-rank/timeout internals, PT2 recompile, and GPU memory layout are not described here.

### Recurring failure modes

- **`-1` resume after MRB/SEV reset** — a Model Rebase or SEV reset clears the Parent lineage root while retry state still holds `-1`, so resume dies with `ModelStoreDBRecordNotFound` (S675238, model 2137792444; D108525530, D108539042).
- **TMS transient failures on register/start** — a single downstream-dependency timeout previously propagated uncaught and failed the whole flow (D108348708).
- **elastic-agent D-state after rank SIGSEGV** — recurring zombie/stuck job; easy to misclassify as a GIL hang (S667567, model 2125081901; D106556357).
- **RE-lowering crash with no exception** — transient-vs-deterministic ambiguity (D106022976).

### Key knobs & design decisions

- **`-1` = latest sentinel; `None` = store-native latest** — not interchangeable; resolve `-1` to a concrete version pre-store (D108525530).
- **Retry+backoff on transient TMS** — `_call_tms_with_retry` wraps the 5 mutation calls with async exp-backoff+jitter, retrying only `DEPENDENCY_TIMEOUT`-class `TMSClientException` (D108348708).
- **`dry_run` made required** (default removed) on cleanup/transition functions (D106623230).
- **Registry knobs:** `uses_online_training`, `criticality_override` tier, PG routing, per-model alert thresholds (D106717796, D106719175).

## Streaming & Model Publish

### How it works

OT models keep serving predictors fresh by continuously publishing trained weights from the trainer to predictors. Two publish granularities: a **FULL_SNAPSHOT** is complete model state, emitted on a periodic cycle (SLO target ~60m, though retrieval/STUS models legitimately run slower/irregular — ~77m, up to ~141m, D107405641, D108105695). Between snapshots, **delta publishes** stream incremental updates: **SPARSE_DELTA** (embedding-table rows) and **DENSE_DELTA** (dense weights). Which deltas a model emits is per-model — many retrieval (UMIA-I2I / HSTU / STUS) models publish FULL_SNAPSHOT only and emit no delta data (D107651869, D107403198).

The publish path runs through **SilverTorch (ST)**, with **Prime** as the newer rewrite being migrated toward prod parity (SS CS Omni migration, D108374581). Production full+delta publishes run via the `st_update_service` entry point (`--online-training`), distinct from the offline `mrs_stand_publish.py` path (D108444892, D107436725). SilverTorch exposes publish types via `use_fused_solution` / `gpu_publish` / `enable_torch_script_publish` (CPU vs GPU_TORCH_DEPLOY / GPU_TGIF_DEPLOY / GPU_TS) (D108219030).

The delta stream is carried over **Hedwig** streaming to predictors; the trainer-side `WeightsDeltaPublisher` serializes per-FQN tensors and ships them via a quick-streaming path (`_send_delta_via_quick_streaming`) or a "normal path" (D106903984, D107678546). The newer **in-trainer publisher** (`STOneFlowInTrainerAsyncPublisher`, `TGIFInTrainerPublisherAsync`) captures live trainer state — a ROSM-wrapped module, gathered dense weights, a representative item pool — and ships it into a publish subprocess across the spawn boundary, avoiding a 5+ minute checkpoint reload per cycle (D107740567, D107740571, D107740564). **Multicast** lets one trainer stream to multiple predictors; **heterogeneous multicast** filters each predictor's sparse stream to only the tables it serves via a skip set (D106903984, D105270803, D105278659). Retrieval/streaming models additionally build a **FreshIndex / bloom filter** over filter features read from Scribe for between-snapshot item freshness (D108119268, D105198769).

### Recurring failure modes

- **Publish blocking training QPS.** When delta Phase 2 (async CPU publish via Hedwig/Manifold) overruns the publish interval, the training thread blocks in `may_wait_for_ongoing_task_done()` for 20+ min, dropping QPS toward zero (D107207628, D107678546, D107100217). Hedwig **publisher buffer overflow** caps streaming success at ~20% (~80% TIMEOUT), fixed by enabling adaptive **flow control** (D108141457, D106118273, D107167718 KI-002).
- **Collective deadlock on publish failure.** A failure path running rank-asymmetric work (`shutdown()`, `_validate_model_state()`, item-delta gather/all-to-all) before raising strands fast ranks while a slow rank is mid-collective — permanent hang / Gloo timeout. Fix: pre-push `all_gather_object` error-sync barrier and raise the terminal exception *before* cleanup (D108538046, D105191849, D105606332, D106022977).
- **OOM in the publisher.** Bloom/FreshIndex build and the gather/`torch.save` phase blow memory: 604 GiB on an 80 GiB GPU (D108119268), FP32 trigger embeddings (~360 GiB) surviving into save (D105407903), retained unquantized rows (D106873154, D106873155).
- **Parity / determinism gaps (Prime↔prod).** Byte-diverging serving graphs from missing lineage fields, wrong float-feature threading, sorted-vs-emit-order bloom columns, copy-pasted dtypes (D108370847, D108371217, D105198769, D106826725). `--enable-determinism` was missing from the prod code path (D108444892).
- **Snapshot staleness from quota / starvation.** Manifold checkpoint quota exhaustion (`DCPTraitsWrapperException`) gaps FULL_SNAPSHOTs for hours (P59, D107567634); Scribe/DPP starvation stalls publishing (D108195174, D107594279).
- **Monitoring false positives.** Detectors expecting deltas a model never publishes, or reading NULL `publish_mode` for retrieval models in `dai_modelstore`, page chronically (D105893378, D107403198, D107672307, D105385735) — UMM/`meta ai.model.instance` is ground truth.

### Key knobs & design decisions

- `publish_interval_secs` — base delta cycle for **both** sparse and dense; dense interval = `dense_weights_publish_interval_cycles * publish_interval_secs` (D107541618).
- `embedding_delta_percentage` (1.0 = full delta), `send_sparse_delta_via_normal_path`, `enable_quick_streaming` (D107207628, D106903984).
- Hedwig **adaptive flow control** via `use_adaptive_flow_control` JustKnobs + `hedwig_peer_config.mcconf`; publisher-activity threshold (10s) so chunked sparse publishers aren't marked inactive (D106118273, D107700120).
- `scribe_read_timeout` (raised to 240s for ST2); per-cycle Scribe read-window differs ST1.0 vs ST2.0 (D107071026); FreshIndex `num_readers` / `max_queue_size` (D106850425).
- `elastic_publish_stage` gates dense-delta; `snapshot_counts` declares expected per-type counts for SLIs (D106406191, D105893378).
- HW pinning (A100/H100/ZionEX over `TC_ANY_80G`) for consistent publish memory/QPS (D108371525, D107108181, D106199340); publish GPU topology right-sizable (4x8→2x8, D105319531).
- `max_consecutive_full_publish_failures` tolerates transient TGIF failures (D106022978, D106022975).
- ST snapshot lineage kwargs (`checkpoint_model_entity_id`, etc.) on `create_model_instance`, resolved at load time, are required for sparse-delta multicast correctness; the misleadingly-named `checkpoint_*` bulk-eval-restore fields are a distinct concept (D106826725, D107104375, D107104405).

## Freshness & Retrieval

### How it works

In OT, "freshness" is the ability of a retrieval model to surface very recently created items before the next full index rebuild. The platform runs a **dual-index ("fresh cascade") retrieval path**: a small **fresh index** carrying just-ingested items alongside the large **main index**, merged downstream. Reference target: IG Reels Tab SS Omni retrieval (`ig_reels_tab_ss_omni_retrieval`, UMIA; D106448585, D106443920).

Retrieval is **KNN over embeddings**. Each request runs two KNN lookups — main and fresh — and a postprocess step (`freshness_knn_postprocess_*`, `update_res_with_merged_embedding_tensor`) merges the result sets (D106539263, D106026263). The **embedding cache** holds item embeddings consulted during the merge; the fresh index has its own cache separate from the main item-emb cache (D106026263). For semantic-id (FBR Oneflow) retrieval, a **`CompositeSidTrie`** holds two shards: `_module_list[0]` = fresh, `_module_list[1]` = main; the fresh shard is small (~`realtime_index_size`) and uses `BINARY_SEARCH` for low-latency on-device lookup (D106451558). The **"Invisible Fresh Index"** design pairs per-cluster fresh sub-buckets with main clusters via UMM centroid lookup (D106448585, D105981856).

### Recurring failure modes

- **Cross-source duplication.** Main and fresh KNN run over separate indices, so an item in both produces a downstream duplicate; the merge originally didn't dedup. Fix: `dedup_main_with_fresh` (`@torch.fx.wrap`) where the fresh copy wins (more up-to-date) (D106539263). The core retrieval-correctness staleness trap.
- **Serving-latency regressions from device placement.** A ~733 MB Device-to-Host copy fired every request between the two `gather_data_from_main_and_fresh_index` calls, dominating p99; root cause was fresh_index cache placement vs item-emb cache. Fix: place fresh_index cache on CPU when item-emb cache is on CPU (D106026263). Conversely, demoting the fresh semantic-id lookup off GPU cost two host round-trips per query (D106451558).
- **TorchScript/export breakage.** `_log_fresh_reranker_merge_stats` (a `@torch.fx.wrap` helper) called the global `logger`, invisible inside the wrapped fn under TorchScript → `RuntimeError: attribute lookup is not defined ... 'Logger'` (D106408578).

### Key knobs & design decisions

- **`realtime_index_size`** sizes the fresh shard/index (D106451558).
- **Fresh-shard lookup = `BINARY_SEARCH`**, CUDA params kept on GPU to avoid host round-trips (D106451558).
- **Cache-placement coupling** — fresh_index cache follows item-emb cache device (D106026263).
- **`@torch.fx.wrap` helpers must be TorchScript-safe** — no global captures (D106408578).
- **Fresh-wins merge policy** on collision (D106539263).
- Video-age-based sorting (`most_vpv_1d_preferred`) is an emerging freshness signal (D107972614).
- STUS / ingestion-pipeline timing knobs (num_readers, timeouts, queue sizes) are **underspecified in corpus**.

## Reliability, Alerting & Oncall Mechanisms

### How it works

OT reliability is a layered alerting stack feeding an LLM triage agent that sits *between* detectors and the human oncall. Core monitored signals are **job liveness, failure rate, publish/cycle freshness, and end-to-end (E2E) latency**:

- **Training-QPS liveness:** pages when `dpp_worker.num_examples_read.sum.60` stays at 0 for 60 min on baseline/holdout/launch-candidate models — a zombie-job detector routed to the centralized `mrs_online_training` rotation (D106454858).
- **Failure-rate SLI:** IG OT PROD jobs scored against `ig_training_failure_rate` (Scuba `job_type = ONLINE_TRAINING`, 60s buckets), SLO `failure_rate <= 0.05` for 95% of buckets daily; `PREEMPTED_BY_MAST`/`KILLED_BY_USER` excluded so infra preemption isn't counted as model failure (D105193312, D106548704, D106681946).
- **Publishing/trunk stability:** alerts keyed to a model's `cycle_minutes` fire when publish cadence stalls (D106755615); trunk observers at 1d/2.5d/4d windows (D107283032).
- **E2E latency:** per-cell `max_latency_secs` thresholds, with separate holdout knobs (holdout cells are noisier) (D105282252, D105272268).

The **escalation ladder is the central design pattern**: detectors fire a WARNING tier *below* MAJOR to buy the agent a window to auto-triage/auto-mitigate before paging — OT publishing WARNING at 1.2× the cycle window (~80 min head start, D106755615), trunk WARNING at 0.8× the MAJOR threshold (D107283032). MAJOR pages; WARNING goes to the agent, which matches against R-rules/P-patterns + recovery docs with dashboard links (D107420414, D106191904). SEV response appears as prevention/follow-up checks (pre-launch HW validation to block `TC_ANY`, D106704835) and retry/backoff hardening of config-mutation chokepoints (D108337795).

### Recurring failure modes

- **Zombie/stalled jobs** — RUNNING but 0 examples read; caught by the QPS=0 net (D106454858).
- **Snapshot/freshness staleness** — publish overruns caught by cycle-window alerts (D106755615).
- **False pages from miscalibrated detectors** — `_retrieval` models never emit SPARSE_DELTA by design (D107153849); `checkpoint_training_data_age_mins` has a 7h timezone+scope bug on OT jobs (D105616982); duplicate publishing alerts fire twice per model_id (D106049931); chronic 5–8% degradation warrants SLO review not a page (D106537982); holdout E2E noise runs ~3.6× baseline, ~80% of alert volume (D105282252).
- **Mitigation mis-verification** — citing a SEV mitigated from in-thread status text instead of the canonical `time_mitigated` field propagated wrong guidance across 5 archives (D105615868).
- **Transient infra throttle** — RE throttle hard-failing un-retried config submits (D108337795).

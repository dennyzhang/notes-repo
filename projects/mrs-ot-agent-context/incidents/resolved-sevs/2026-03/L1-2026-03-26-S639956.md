## Incident impact
Online Training data volume for Threads Feed, TIXU, and Search ranking paths dropped to near zero for ~9 hours. This caused degradation in Feed and TIXU models and engagement metric regressions (Likes ~6.5%, Impressions ~4.7%, Reshare ~9.5% avg hourly variance w/w)

## Root cause
Threads Feed, TIXU, and Search all share a common LSR ranking code path implemented in the DistilleryTextPostAppRankerMez class (ranker_mez.py (https://www.internalfb.com/code/fbsource/[a27bb24d058e]/fbcode/instagram-server/distillery/text_feed/ranking/ranker_mez.py?lines=4942)). A key method is async_rank_media (https://www.internalfb.com/code/fbsource/[a27bb24d058e]/fbcode/instagram-server/distillery/text_feed/ranking/ranker_mez.py?lines=4942), which orchestrates the full LSR ranking pipeline. This method does two things: (1) rank content for the user, and (2) log the ranking signals as training data so that ML models can continuously learn from real-world outcomes. The training data pipeline feeds the Online Training (OT) loop for all Threads relevance models (ESR, LSR, VM MTML, Retrieval, etc.). An overview of the callstack: 
Inside async_rank_media, the ranking_logger is the key object that connects the ranking step to the training data logging step:                                                                                                                                                                                                                                                                                                                                                                                                               
Initially: ranking_logger is set to None at the top of the method (https://www.internalfb.com/code/fbsource/[a27bb24d058e]/fbcode/instagram-server/distillery/text_feed/ranking/ranker_mez.py?lines=5205) (it actually should never be None, see below).
Rank (RAAS path): Inside a subsequent if/else conditional branch (in both sides of the conditional) the code creates a ranking_logger (https://www.internalfb.com/code/fbsource/[a27bb24d058e]/fbcode/instagram-server/distillery/text_feed/ranking/ranker_mez.py?lines=5205-5206%2C5237%2C5251%2C5259-5260). The logger is then used to call ranked_media.raas_log_model_data() to log the model's prediction scores.                                                                                                                                        
Log Training Data: Much later in the method (after control layer processing, filtering, etc.), _async_log_training_data is called (but critically only if ranking_logger is not None (https://www.internalfb.com/code/fbsource/[a27bb24d058e]/fbcode/instagram-server/distillery/text_feed/ranking/ranker_mez.py?lines=5350-5353%2C5360-5363%2C5373-5375%2C5386-5389)), which writes the full training feature vector to Scribe. This is actually bug-prone logic, as the ranking_logger should never be None. See T261646941 for a fix. From _async_log_training_data, the data flows to Muddler tables (e.g., ig_muddler_generic_training_data_text_post_app_*), which are consumed by the Online Training (OT) pipeline to continuously update all Threads relevance models.
D96993922 extracted inline code from async_rank_media into a helper method _create_lsr_ranking_logger_and_log. Critically the creation of the ranking_logger was moved to this helper method, and ranking_logger remained None in the main flow caller. The downstream _async_log_training_data call (guarded by the buggy if ranking_logger is not None check) was silently skipped. This caused no training data logging for Threads Feed, TIXU, and Search ranking paths and subsequent degradations in corresponding Threads Relevance models.

## Remediation
TLDR: The root cause diff was identified and reverted, D98295929, restoring training data volume. The corrupted training data window was blocklisted across all affected clients (Feed, TIXU, Search) to prevent OT from consuming bad data. Corrupted model snapshots were banned and OT was restarted for all affected prod/holdout models (Retrieval, ESR, LSR Main/VM/Debias MTML). Most model metrics recovered within hours; ESR P(skip)/P(continue) took several additional days to recover. Notifications, Replies, and Graph were not impacted.

## Overview
RaaS config of TaskBrew12 model launch accidentally triggered inference to a legacy model.
Before the code change, the legacy model served no traffic; after the code change, the legacy model started to serve the same traffic as prod VM MTML model.
The sudden increase in cpu usage led to model client error rate and high SR fatal rate. 
After reverting the launch diff, we see model traffic dropped and client error gone.

## Incident impact
SR Fatal rate increased for over 1hr

## Root cause
Indicated https://fburl.com/code/aqtdnbfy, E(post tap and like count) was in tb9, but removed in tb11, and added back in tb12. So the default model will fallback to tb9 model. Since we only landed the launch config first, but haven't rolled out TB12 model, all traffic will start to call tb9 because of this signal.

## Remediation
SR Fatal rate recovered after unlanding the diff

## Prevention
We should review materialized json files more carefully during model launch.
Specifically:
Check the conditional model map for newly added signals as well as existing signals.
Make sure the model sequence is in the order of launch sequence, i.e., new_prod -> old_prod -> holdout
For future prevention, we also masked all event terms in the legacy model D92849115 (https://www.internalfb.com/diff/D92849115), so that it won't be called under any circumstances.

## Overview
Incident Impact
End-User Experience: No direct end-user impact. This was an internal ML model release pipeline failure. The mvai/video_udd_lsr model release was delayed for 5 days, preventing the latest model snapshot from reaching production. Per the SEV3 criteria for discovery models (https://docs.google.com/document/d/10kawZuw5eAzpFm8ZvT8Hgy-wfx-Cjw1sPtcLJ_70wOY/edit?tab=t.0#heading=h.crdic255g43x), a delay exceeding 4 business days qualifies as SEV3.
Product Metric Impact: The video_udd_lsr model release R4117.2 was blocked at the serving eval gate. The Vanguard serving eval job (test case 1462247435502561 (https://www.internalfb.com/vanguard/serving_test_cases/1462247435502561)) failed with response_generator exit -11 (SIGSEGV), preventing the model snapshot from being validated and released through the mvai/video_udd_lsr conveyor (https://www.internalfb.com/conveyor/mvai/video_udd_lsr/releases/4117.2/). 
Overview
The crash was caused by the lack of guard and fallback logics in the  ServingEvalDataGenerator.cpp code:
- Serving eval has a existing code to pull metadata from the predictor. The response type is PyTorchModelMetadataResponseand the legacy code takes metadata from PyTorchModelMetadataResponse->argumentNames()
- metadataResponse->argumentNames() began returning an empty vector (possibly an upstream metadata service change) 
- The existing code at line 150 assumed this would always be populated and used it to reorder input_metadata. With an empty list, the subsequent createPredictionRequestInput() function attempted to look up argument names in an F14FastSet constructed from an empty get_fixed_argument_names() vector, leading to a hash lookup on invalid data and a segfault.
Causal chain:
Upstream metadata change >> argumentNames() returns empty >> no fallback logic >> fixed_argument_names also empty >> F14FastSet hash lookup on invalid data >> SIGSEGV in createPredictionRequestInput() at line 580 >> response_generator exit -11 >> serving eval fails with INF-309

## Root cause
The createPredictionRequestInput() function at ServingEvalDataGenerator.cpp:580 constructed an F14FastSet<std::string> from modelMetadata->get_fixed_argument_names(). When this returned an empty vector, the subsequent iteration over koski data column names and lookups into this set operated on an inconsistent state. The original code at line 1041-1043 was:
folly::F14FastSet<std::string> args(
    modelMetadata->get_fixed_argument_names().begin(),
    modelMetadata->get_fixed_argument_names().end());

With no fixed argument names, the set was empty, and the function could not correctly determine which columns to include in the prediction request, leading to a hash lookup on invalid data and SIGSEGV.

The fix_input_metadata_order() function at line 155 was called with args from metadataResponse->argumentNames(). When argumentNames() returned empty, fix_input_metadata_order() was skipped (the if (!args.empty()) check at line 155 already existed), but this meant fixed_argument_names was never populated. The original code at line 150:
const auto args = *metadataResponse->argumentNames();

did not check for empty — it simply dereferenced the vector.

The serving eval data generator was originally written under the assumption that upstream metadata responses would always populate these fields. There were no invariant checks (CHECK(!args.empty())) or fallback data sources. The Thrift default value semantics (empty dict = default, not "explicitly set") were not considered in the control flow. The crash location (folly hash internals) was far from the logical error (empty metadata), making diagnosis slow.

## Remediation
D94008445 (https://www.internalfb.com/diff/D94008445)  fixed the above issues:
1. backfills argument names from metadataResponse->pyTorchModelMetadata()->argument_names(), cross-referencing against input_metadata to include only valid arguments. This provides a robust fallback data source when the primary argumentNames() field is unpopulated. Added logging ("No argument names found in metadata response, backfilling from argument_names") for future diagnostics.

2. The fix first checks modelMetadata->has_fixed_argument_names(). If not set, it falls back to building the set from modelMetadata->get_input_metadata() arg names, with a WARNING log indicating the fallback.

## Prevention
Added unit tests for ServingEvalDataGenerator covering edge cases: empty argumentNames(), empty preprocMetadata, missing fixed_argument_names, and their combinations 
Leverage CC to scan the serving eval codebase to identify and fix other implicit assumptions or potential bugs, also guarded with unit tests

**Adversarial verdict: REJECT — 2 FATAL flaws:**

1. **NOISE and TRANSIENT are not valid verdict field values — schema mismatch (FATAL).** The production verdict schema is `PAGE | MONITOR | NO_ACTION | UNKNOWN | DETECTOR_BROKEN` (from ot-sev-monitor/ot-alert-monitor prompts). NOISE and TRANSIENT are class labels (class field in diagnosis output), NOT verdict field values. The rule's exempt list includes them as verdicts — creating an escape hatch that never triggers because the production agent never emits `verdict=NOISE` or `verdict=TRANSIENT`. The exemption is dead code; it looks correct but provides no protection. A hallucinating agent emitting NOISE/TRANSIENT as the verdict field (schema violation) would bypass the entity requirement through this dead path.

2. **CONVEYOR_REGRESSION exempt clause conflicts with PAGE branch (FATAL).** CONVEYOR_REGRESSION is a class label, not a verdict value. When an incident has class=CONVEYOR_REGRESSION and verdict=PAGE (a real occurrence — conveyor blocked upstream of OT, real OT action needed), the v3 rule exempts entity requirement (the class match fires first) while the PAGE branch simultaneously requires one. The rule is self-contradictory for this case; which branch wins is undefined.

3. **UNKNOWN verdict has no entity-requirement mapping (WARN).** UNKNOWN (triage inconclusive) is not in the required-entity list or exempt list. An agent emitting verdict=UNKNOWN for a real OT failure falls through with no guidance — either it's over-penalized (grader demands entity for an ambiguous case) or the rule is silently unenforced.

### Decisiveness v4 redesign (for iter5)

Root fix: eliminate class labels from exempt list. Use only the canonical verdict field values. Clarify UNKNOWN handling.

> **DECISIVENESS RULE v4:** When `verdict=PAGE` (action required): include in root_cause AT LEAST ONE specific entity — a CLI command with ACTUAL IDs verbatim from the incident body (not placeholder templates), a specific unixname to page, or an upstream SEV ID (e.g., S668542). Exception: if the incident body contains no MAST job name AND no model identity is confirmed, the phrase "no MAST job name in body — cannot construct job-name CLI" IS sufficient; it documents the blocking gap without fabricating. When `verdict=MONITOR` (investigation needed): include the specific metric query or log command with the ACTUAL job name from the body (not a placeholder). When `verdict=NO_ACTION`, `verdict=UNKNOWN`, or `verdict=DETECTOR_BROKEN`: "alert config fix needed" or "no OT-side action" suffices — no entity required. If the incident body contains no MAST job name, state that explicitly rather than constructing one from a model ID or model type. NOTE: NOISE, TRANSIENT, CONVEYOR_REGRESSION are class labels not verdict field values — if triage outputs verdict=PAGE on any class, the PAGE entity requirement applies without exception.

**Adversarial verdict: REJECT — 2 FATAL flaws:**

1. **Wrong flag on model-series fallback — `--model-type=type` does not exist (FATAL).** Every reference in triage-discipline.md, ot-failure-mode-catalog.md, and all cron backups uses `meta ai.model describe --model-id=<id>`. STUS is the execution mechanism; its owner is the STUS team, not the model owner who should be paged. R19 establishes the STUS exceptions as routing to the MODEL owner (who owns the retrieval index publishing pipeline), not the STUS infra team.

3. **model_owner_unixname frequently empty, no fallback in PAGE path (WARN).** Memory entry `model-enrichment-use-registry` documents this: `meta ai.mast-job metadata` often returns empty model_owner_unixname. Without a fallback, the PAGE path silently produces an empty owner string, which the grader scores as 0.

### OwnerRouting v5 redesign (for iter5)

Root fix: correct CLI flag; fix STUS REAL_OT_FAILURE owner to model owner not STUS job owner; add empty-metadata fallback.

> **OWNER ROUTING RULE v5:** For `verdict=PAGE` (OT-side action confirmed):
> - If a verbatim MAST job name (matching pattern `mvai-training-online-*`) appears in the incident body: owner = `meta ai.mast-job metadata --name=<verbatim_name>` → use `model_owner_unixname` field. If empty or field absent → "mrs_online_training (pending model owner resolution)". Do NOT construct a MAST job name from a model ID.
> - Fallback (model ID or type known, no verbatim MAST name): owner = `meta ai.model describe --model-id=<model_id>` → use `model_owner` field. If empty → "mrs_online_training (pending model owner resolution)".
> - If model identity is fully ambiguous: owner = "mrs_online_training (pending model identification)".
>
> For `verdict=MONITOR`: owner = "mrs_online_training (monitoring)".
>
> For `verdict=UPSTREAM_INFRA` (cascade): owner = the upstream oncall rotation handle IF explicitly named in the body (e.g., "ZippyDB oncall" → "zippydb oncall"); otherwise = "upstream infra oncall". Do NOT infer oncall identity not in body.
>
> For `verdict=NO_ACTION`, `verdict=DETECTOR_BROKEN`: owner = "none (no OT-side action; alert config fix needed separately)".
>
> **STUS exception (ig_reels_tab_ss_omni_retrieval, ig_reels_starsearch_t2i_retrieval):**
> - Upstream Scribe/ZippyDB SEV confirmed in body → UPSTREAM_INFRA; owner = upstream SEV oncall from body.
> - No upstream SEV confirmed in body → REAL_OT_FAILURE (P50 — STUS/publish failure); owner = MODEL owner via `meta ai.model describe --model-id=<model_id>` (NOT the STUS MAST job owner — STUS is the execution mechanism, the model owner is who to page).

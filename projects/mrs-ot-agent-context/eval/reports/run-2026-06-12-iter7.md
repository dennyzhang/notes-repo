## Decisiveness v8 — REJECTED

**Fatal flaws:**

1. **Unixname-as-entity under-constrained (FATAL).** Rule allows "a unixname that appears verbatim in the body" as a valid PAGE entity. Incident bodies always contain reporter/author unixnames. A triage agent can satisfy the entity requirement by citing the reporter — not the model/job owner — producing PAGE with `root_cause: "impacting unixname:jdoe"` where jdoe is the filer, not the failing system's owner. No constraint that the unixname must be model owner or OT oncall.

2. **MONITOR rule has no fallback (FATAL).** PAGE has an explicit fallback ("no MAST job name or model ID in body" is sufficient). MONITOR says root_cause MUST reference "specific metric, log command, or entity from the body." If the body contains none of those (bare narrative: "streaming success rate looks off, please investigate"), the agent cannot satisfy the rule without fabricating content — which is forbidden. Structural dead-end with no fallback phrase.

**Warnings:**
- TRANSIENT+PAGE with entity gap phrase — technically compliant but operationally low-value (not fatal; rule is internally consistent)
- UNKNOWN+REAL_OT_FAILURE allows no entity, creating a verdict-shopping vector (pick UNKNOWN over PAGE to skip entity discipline)

## OwnerRouting v9 — REJECTED

**Fatal flaws:**

1. **Path B entitlement guard missing (FATAL).** Path B fires when incident "concerns ig_reels_tab_ss_omni_retrieval or ig_reels_starsearch_t2i_retrieval" but does not specify the identifier must be a model_id. If the body contains only an entitlement string (e.g., `ig_reels_prod_tab_ss_omni_retrieval_v3`), Path B invokes `meta ai.model describe --model-id=<entitlement>` — which either errors or returns wrong data. Path D explicitly guards against entitlements; Path B has no equivalent guard.

2. **Path C vs D owner divergence undetected (FATAL).** When BOTH a MAST job name AND a model_id appear in the body, first-match fires Path C (MAST job owner). A MAST job relaunch, rebase, or cross-team eval run can produce a job owned by an infra/tooling team while the model_id belongs to a product team. Rule silently pages the wrong owner with no reconciliation check.

**Warnings:**
- Path A "explicitly names" undefined — "possible ZippyDB impact" is ambiguous; rule gives no guidance on hedges
- DETECTOR_BROKEN → "none" suppresses detector repair routing (not wrong by schema, but operational gap)

## Decisiveness v9 design (for iter8 A/B, if operator opts to continue)

Root fixes: (1) remove unixname from valid entity types; (2) add MONITOR fallback phrase.

> **DECISIVENESS RULE v9:** When `verdict=PAGE` (action required): root_cause MUST name at least one specific entity drawn from the incident body. Valid entities: (1) verbatim MAST job name from the body, (2) verbatim model ID from the body, or (3) verbatim upstream SEV ID (format S<digits>) from the body. Do NOT use reporter/author names or any unixname that is not a model ID or job name. Do NOT fabricate any of these. If the incident body contains no MAST job name, no model ID, and no upstream SEV ID: state "no entity in body (no MAST job name, model ID, or upstream SEV)" as the entity gap — this is sufficient for PAGE. When `verdict=MONITOR` (investigation needed): root_cause MUST reference the specific metric, log command, or entity being monitored from the incident body; generic "please investigate" is insufficient. If the body contains no specific metric, log command, or entity: state "no specific metric or entity in body — investigation scope unspecified" as the monitoring gap. When `verdict=NO_ACTION`, `verdict=UNKNOWN`, or `verdict=DETECTOR_BROKEN`: no entity required — "alert config fix needed" or "no OT-side action" suffices. Exception: class=NOISE or class=OUT_OF_SCOPE implies verdict=NO_ACTION; these cases require no entity.

## OwnerRouting v10 design (for iter8 A/B, if operator opts to continue)

Root fixes: (1) add entitlement guard to Path B; (2) add dual-owner note to Path C/D conflict; (3) clarify Path A hedge-phrase handling.

> **OWNER ROUTING RULE v10:** For `verdict=PAGE` (OT-side action confirmed), apply the FIRST matching path:
>
> **Path A — Upstream cascade:** If the incident body explicitly names an upstream cause with a concrete identifier (ZippyDB failure, Scribe outage, infrastructure SEV ID format S<digits>): owner = the upstream team named in the body, or "upstream infra oncall" if no team is named. Hedge phrases ("possible ZippyDB impact", "ZippyDB-adjacent") do NOT trigger Path A. Do NOT infer an upstream team not in the body.
>
> **Path B — STUS retrieval models:** If the incident body contains the verbatim model_id `ig_reels_tab_ss_omni_retrieval` or `ig_reels_starsearch_t2i_retrieval` (not an entitlement string ending in _prod, _prod_v<N>) AND no upstream cause explicitly named in Path A: owner = `meta ai.model describe --model-id=<model_id_from_body>` using `model_owner` field. If empty → "mrs_ig_retrieval_oncall".
>
> **Path C — Verbatim MAST job name:** If a verbatim MAST job name (pattern mvai-training-online-*) appears in the body: owner = `meta ai.mast-job metadata --name=<verbatim_name>`, try `model_owner_unixname` then `model_owner`. If both empty AND a model_id also appears in the body → fall through to Path D for model-based owner lookup.
>
> **Path D — Model ID:** If a model ID (not an entitlement string ending in _prod, _prod_v<N>) appears in the body: owner = `meta ai.model describe --model-id=<model_id>` using `model_owner` field. If empty → "mrs_online_training (pending)".
>
> **Path E — Fallback:** owner = "mrs_online_training (pending model identification)".
>
> For `verdict=MONITOR`: owner = "mrs_online_training (monitoring)".
> For `verdict=NO_ACTION`, `verdict=DETECTOR_BROKEN`: owner = "none (no OT-side action)".
> For `verdict=UNKNOWN`: owner = "mrs_online_training (pending triage)".

Targeted cases for iter8 A/B: ALERT-1201406268614142, ALERT-1533487445064477, A1703030847735006, ALERT-1427819186056622, S665454.

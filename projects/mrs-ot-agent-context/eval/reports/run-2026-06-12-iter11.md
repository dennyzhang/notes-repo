### Strategic pivot: R26 owner-routing SKILL.md update

**Why this target:** The task explicitly says "stop grinding owner-routing prose rules; move it to a deterministic capability." The owner score (mean 0.36, ±0.03 noise) has hit its prose-rule ceiling. The structural fix is:

> Add to SKILL.md: "For verdict=PAGE, run `meta ai.model describe --model-id=<model_id>` and use `model_owner` field as owner. Fallback: `meta ai.mast-job metadata --name=<mast_job_name>` → `model_owner_unixname`. Final fallback: 'mrs_online_training (pending)'. Run the lookup; do NOT reason about team ownership from body text."

**Expected gain estimate:**
- Gold set: 71/77 cases have specific owners
- Owner scores model-lookup-derivable cases vs non-lookup (upstream cascade)
- Conservative estimate: 20/77 cases improve from 0→1 (those where correct owner IS model_owner from lookup)
- Owner dimension gain: 20/77 × 1.0 = +0.26 on owner dim → +0.039 on composite (0.26 × 0.15)
- Optimistic: 0.033–0.050 composite gain
- **Both estimates exceed the ±0.029 noise band**

**Why this is different from Dec/Own prose rules (v1–v9):**
- Not a prose reasoning rule with branches → fewer adversarial attack vectors
- One mechanical instruction: "run this CLI, use this field"
- Doesn't need to reason about WHICH team owns an upstream service
- The lookup IS the rule

**Adversarial risk:** Low — the rule is unconditionally "run the tool, use the field." The only failure mode is when model_id isn't in the body (handled by fallback chain). No conflicting conditions.

**Caveats:**
1. Eval agent must actually call `meta ai.model describe` during eval (has tool access via workflow subagent)
2. Gold set ground truth must match `model_owner` field format (some GT has "ronghuang", some has "ronghuang / p92_relevance_retrieval_oncall")
3. For upstream cascade cases (S667358 owner = Scribe/ZippyDB), lookup would return model owner (wrong answer) → those cases might regress
4. Must A/B on a stratified sample that isolates model-owner cases from upstream-cascade cases

**R26 design (for iter12):**

> **OWNER LOOKUP RULE (R26):** For `verdict=PAGE`: owner = result of running `meta ai.model describe --model-id=<model_id_from_body>` → `model_owner` field. If model_id not in body, try `meta ai.mast-job metadata --name=<mast_job_name_from_body>` → `model_owner_unixname`. If still empty → "mrs_online_training (pending model id lookup)". For `verdict=NO_ACTION` / `verdict=MONITOR`: no lookup required — set owner to the detector owner or "mrs_online_training". EXCEPTION: if the incident body explicitly names an upstream service outage (ZippyDB, Scribe, upstream SEV S<digits>) as the root cause → owner = "upstream infra oncall" (skip the model-owner lookup; the model owner is not the person who should act on an upstream outage).

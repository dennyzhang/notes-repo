## What was done

### 1. GRADE schema update — COMMITTED (notes b7046d97d998)

Added `next_action_quality` field to the GRADE schema in both the daemon copy (`~/.myclaw-ot-bot/eval-flow.js`) and canonical notes copy (`eval/eval-flow.js.txt`). Both synced.

**Why**: Decisiveness dim was measured by `isActionable(verdict)` — a binary flag on verdict type. This cannot distinguish between a KNOWN_PATTERN verdict that says "check logs" from one that says "run `meta ai.mast-job error --name=prod_model_v12 --version=45 --no-truncate -o json`". The `next_action_quality` field lets the grader score this distinction.

**Changes:**
- `GRADE` schema: added `next_action_quality` (0/0.5/1) to properties + required
- Grader prompt: added scoring instruction for `next_action_quality` (1=specific entity, 0.5=named step, 0=generic/missing; NOISE/OUT_OF_SCOPE verdicts score 1 to avoid penalizing appropriate silence)
- Decisiveness calculation: now uses `next_action_quality` when present (v2); falls back to `isActionable(verdict)` for cached/legacy results (v1)

**Baseline impact**: The decisiveness dim will shift on the next full-60 eval because it's now measuring next-action specificity (0/0.5/1 scale) vs. the old binary actionable-verdict check. The shift direction is unknown until the next full-60 run — the GRADE schema update is a measurement improvement, not a triage rule change.

### OwnerRouting v3 redesign (for iter3)

The core mechanism (calling meta CLI for owner) works in 4/12 cases without hallucination. Root problems:
1. Must call BOTH `meta ai.model-series metadata --model-type=<TYPE>` (model-series owner) AND `meta ai.mast-job metadata --name=<JOB>` (job owner); prefer MAST job owner if both present and different.
2. For UPSTREAM_INFRA: owner = SEV oncall from the body ONLY; do NOT infer SEV status/closure not explicitly stated.
3. For DETECTOR_BROKEN where no OT action needed: owner = "none (no OT-side action)" not "PE MRS".
4. Add a "minimum confidence" gate: if the meta call returns a name with confidence <0.7, fall back to team name rather than individual.

Draft v3 rule:
> OWNER ROUTING RULE v3: For REAL_OT_FAILURE / KNOWN_PATTERN (OT-side fix required): call `meta ai.mast-job metadata --name=<JOB>` to get owner unixname; only if no MAST job name available, fall back to `meta ai.model-series metadata --model-type=<TYPE>`. Set owner to that unixname. For UPSTREAM_INFRA: owner = the upstream SEV's owning oncall team IF explicitly named in the incident body (e.g., "ZippyDB oncall"); otherwise "upstream infra oncall". Do NOT look up or infer SEV closure status not stated in the body. For DETECTOR_BROKEN where verdict is NO_ACTION (healthy model, misconfigured detector): owner = "none (no OT-side action; alert config fix needed separately)". STUS-exception models classified UPSTREAM_INFRA: owner = upstream SEV owner from body.

## Decisiveness v2 rule (designed for iter3)

Based on eval taxonomy correction from iter1 and `next_action_quality` schema now in place:

> DECISIVENESS RULE v2: When verdict is KNOWN_PATTERN (root cause confirmed): include in root_cause AT LEAST ONE specific entity — a CLI command with actual IDs filled in (not placeholders), a specific unixname to page, or a file:line reference. When verdict is NEEDS_INVESTIGATION: include the specific metric query or log command that resolves uncertainty (e.g., `meta ai.mast-job error --name=<actual_job_name> --version=N`). DETECTOR_BROKEN / OUT_OF_SCOPE / NOISE / TRANSIENT: "alert config fix needed" or "no OT-side action" suffices — no entity required. Generic "check logs" / "investigate further" / "monitor" without a named entity = score 0 on next_action_quality.

**Prerequisite**: The `next_action_quality` field is now in the GRADE schema (this run). The Decisiveness v2 A/B can run in iter3.
